v0.1 · 2026-08-29

本篇是整个v0.1文档的入口，只回答两件事：

1. **架构**：RendezvOS 系统框架的概念是什么？其设计思路如何？ 基于 RendezvOS core 的系统在逻辑上怎么分层？core 内部提供了哪些方面的支持？

详细的机制细节不在本篇展开，请参考对应的文档专篇。

## 1. 概述

RendezvOS 是一个**混合内核架构**的**多核**操作系统内核框架。

基于 RendezvOS 框架的操作系统，在内核态保留一个小的**核心框架（core）**：它提供 boot、架构相关硬件设置、内存与地址空间管理、线程/进程抽象、线程间 IPC、中断处理框架等实现操作系统所必要的基础能力，但**不向用户态提供任何 syscall 接口**。凡对用户态可见的 syscall，以及文件管理、网络、各类设备驱动等，都应在 core 之上的**兼容层**实现，而不应放进 core。基于混合内核架构，这些兼容层的代码运行在内核态。

本仓库（及本套文档）只覆盖这个核心框架本身：设计与实现、文档、对兼容层的硬性约束、基本内核测例，以及为最小可观测性所必需的少量代码（例如启动串口）。完整内核由兼容层与 core 按约定进行链接构建。

**设计目的：** 屏蔽复杂的硬件相关工作（启动、上下文切换、中断处理等），封装并发模型并提供统一的多核框架，使兼容层能以「多个单执行流 server + server 之间异步无锁 IPC」的方式协作构建。兼容层可以拟合其他操作系统的 syscall 行为，但**不限于 Linux**——按同一设计目的，也可以拟合如 seL4 等微内核接口风格。

兼容层一侧通常包括：系统调用入口与处理、为支撑这些调用及其他系统功能而实现的单执行流 + 异步 IPC server、以及对 RendezvOS 框架的封装。它对 core 的使用有三条路（可组合）：直接调用 core 公开函数接口（建议再包一层）、按约定与 core 中指定线程做 IPC、或经 core 预留的 hook / initcall 注入。

在名词约定上，本文档用 RendezvOS 指代兼容层+ RendezvOS core。而RendezvOS core（有时候文档会简写成core），指代本文档所在的源码仓库，作为整个系统的core。（如果有时候发生了错误的混用，请结合上下文去理解）

从设计思路上来说，一方面我们是为了兼容层可以使用单执行流 + 异步 IPC方式构建，以简化内核构造的复杂性，另一方面，虽然微内核的设计思路为这种构建方式提供了根本的思路来源，但是微内核的性能问题，以及为了实现微内核在syscall等系统形态上和现代操作系统（如Linux）的巨大差异，让我们思考，将微内核下，内核和用户态服务线程之间的interface，再挪回内核态，同时，对于这种形态下，内核必备的功能，又进行了优化，比如我们将内存管理模块的策略进行内置，同时允许多核之间进行无锁IPC的通信，从而大幅度改善内核的性能。这是一个典型的混合内核及其优化的思路。

源码树见 §5；构建与链接方如何注入见 `01-构建与链接.md`。

## 2. 目标与边界

**core 要做成什么：** 一块可复用的「操作系统原语层」：能启动、能管内存与地址空间、能建线程并调度、能在线程之间传消息、能处理陷阱/中断与多核同步，从而让兼容层把精力放在策略与用户态语义上，而不是从零开始构建。

**core 故意不做：** 用户态可见的 syscall 表与分发策略、某一具体 OS（Linux / seL4 / …）的语义实现、文件系统与网络协议栈、通用设备驱动框架、发行版级动态链接策略等。这些属于兼容层（或更上层）。core 里若出现相关痕迹（例如弱符号空 `syscall`、ELF 加载辅助），那是挂接点或最小支撑，不是「core 已实现该操作系统特性」。

**如何遵循相关边界约定：** 兼容层只应通过公开头文件（主要是 `include/rendezvos/`）使用 core；需要全局串行化的资源，用自建单执行流 server + IPC，而不是把某种 OS 语义写进 core 源码树。头文件的几个子文件夹包含哪些见 §5.2。

构建侧两种用法见 `01-构建与链接.md`。

## 3. 分层与调用方

整个系统从底向上可以看成：**硬件 / 固件 → core → 兼容层（同属内核态）→ 用户态**。本仓库只实现并文档化中间的 RendezvOS core；兼容层在链接时注入同一镜像（见 `01-构建与链接.md`）。

谁读本篇、怎么用：

| 角色 | 期望 |
|------|------|
| RendezvOS core 维护者 | 改 core 相关代码时，同步本篇与相关专篇 |
| 兼容层构建者 | 只依赖公开 API / 约定 IPC / hook；按 §1 三条路径接入 |

兼容层和core有三条协作路径：

1. **直接调公开 API** — 无全局串行化需求时使用，例如为了提升性能，我们直接在core里面考虑了多核下内存管理模块的并发申请内存释放内存，兼容层可以直接调用而无需与一个特定的兼容层内存分配器线程进行通信。  
2. **与约定线程 IPC** — core 提供 port / 消息 / 阻塞，策略和约定线程的实现大部分在兼容层。  
3. **hook / initcall** — 使用 core 的 initcall，在 core 初始化的特定时机跑兼容层的初始化逻辑（见 `03-模块初始化与内核入口.md`）。

## 4. 内核架构（逻辑视图）

§1 描述了在RendezvOS框架下的整体系统分层。本节来描述：RendezvOS core 本身由哪几块组成。

### 4.1 core 包含什么

按这个模型看，core 就是下面八块。

<table>
  <tr>
    <td width="25%" align="center"><strong>内存管理</strong><br>物理页与地址空间</td>
    <td width="25%" align="center"><strong>线程管理</strong><br>线程与每 CPU 调度</td>
    <td width="25%" align="center"><strong>IPC</strong><br>port 与消息</td>
    <td width="25%" align="center"><strong>SMP 及同步</strong><br>per-CPU · 锁 · IPI</td>
  </tr>
  <tr>
    <td align="center"><strong>启动（含 SMP 启动）</strong><br>引导并拉起多核</td>
    <td align="center"><strong>时钟子系统</strong><br>时间与定时器</td>
    <td align="center"><strong>可选平台模块</strong><br>串口 / ACPI / DTB 等</td>
    <td align="center"><strong>构建系统</strong><br>兼容层链入同镜像</td>
  </tr>
</table>

**内存管理** — 物理页面分配，自映射框架，内核与用户地址空间及虚拟内存管理。专篇：`02-内存管理/`（`06`–`12`）。

**线程管理** — 线程抽象（及相关兼容层注入）、每 CPU 调度（及相关调度策略注入）、创建与加载等生命周期开始、核心亲和、生命周期结束。兼容层的 server 均被设计为相应的单执行流线程。专篇：`03-任务与调度/`（`13`–`17`）。

**IPC** — 线程之间用 port 传消息的port及其生命周期管理，包括无锁队列构造的收发、消息的序列化、可选的准入hook，按名字找到port时的名称索引支撑。外部中断在这个模型里，需要同样进行消息的发送，当然，可以直接用注册中断入口的模式。专篇：`04-IPC/`（`18`–`22`），名称索引见 `41`；中断实现见 `23`–`27`。

**SMP 及同步** — 多核跑起来之后的部分：per-CPU 数据、锁与屏障、软 IPI、跨核 TLB。把核拉起来本身归在「启动」，不重复放这里。专篇：`29`–`32`。

**启动（含 SMP 启动）** — 从固件进入RendezvOS框架，完成每核心最早的硬件与页表等初始化，再把其余 CPU 拉起来，直到框架可服务。专篇：`01-启动与初始化/`（`02`–`05`）、`28`。

**时钟子系统** — 基本的时间与定时器部分。专篇：`33`。

**可选平台模块** — 为了能看输出、能认机器而带的一些小工具，可裁剪：串口与日志、ACPI/DTB、ELF 辅助、PCI、PSCI 等。他们本身并不一定是core必须的。专篇：`34`–`39`。

**构建系统** — 让兼容层能跟RendezvOS core链进同一份内核镜像（`EXTRA_OBJECTS` 等），同时和RendezvOS core具有不冲突的一些参数选项，而不是让兼容层另做一套链接脚本。专篇：`01-构建与链接.md`。

### 4.3 几条核心原则

- **策略在兼容层，机制在 core。** 这个和微内核的策略和机制分离是一致的。core 提供内存、线程、port、映射、陷阱入口等前述的一些基本核心模块；而什么时候创建进程、文件系统长什么样等其他的内容，由兼容层实现，并用 §3 的三种调用方式进行组合。  
- **多核按percpu进行管理而非锁。** 在兼容层，应当尽量使用percpu便变量，而尽量避免使用锁，如果需要使用锁，应当尽量使用core里面封装好的方案并使用相应的调用约束，如果有必要，需要进一步的扩展core的内容。  
- **兼容层的启动时注册和运行时分开。** 框架的启动时用initcall来调用兼容层的各类初始化，并通过initcall的level来确定初始化的顺序（同一个level的初始化顺序则难以确定）。在这里需要通过initcall来注入一堆server的线程；真正的server线程的执行要等调度选中。
- **通用抽象和不同ISA的实现分离。** 不同ISA里面需要提供多架构名称相同的一套逻辑 API ，而多架构相同的东西，则会统一进行抽象，放在 kernel/ 文件夹下。

## 5. 源码布局

本小节主要描述`core/` 目录下时，各个顶级子目录主要是做什么的，头文件包含怎么做。

### 5.1 顶层目录

```text
core/
├── include/       对兼容层公开的头文件约定
├── kernel/        与 ISA 无关的共同抽象
├── arch/          按 ISA 划分的架构相关部分
├── modules/       跟架构相关的可配置裁剪的组件
├── script/        各类脚本
├── docs/          文档
├── .clang-format  make fmt依赖的脚本
├── build_env.sh   环境构建脚本
├── README.md      整个core项目的README
└── Makefile       构建入口
```

### 5.2 头文件的区分

`include/`文件夹下包括四个子文件夹

| 路径 | 存放的头文件内容 |
|------|------------------|
| `include/common/` | **公共基础库**：整数类型、链表/树/位图等与具体内核无关的工具数据结构，这个文件夹不应当存在对应的`.c`文件和文件夹 |
| `include/rendezvos/` | **内核公开 API**：内存、线程、IPC、trap、SMP、错误码等兼容层真正该调用的接口，其实质上对应着的`.c`文件夹是`kernel/`。 |
| `include/arch/<isa>/` | **ISA 相关定义**：页表项格式、trap 帧、上下文等架构相关的数据结构定义，对应的`.c`文件夹，就是`arch/<isa>/`下的内容。  |
| `include/modules/` | **可选模块的 API**：由config配置阶段进行模块的选择，生成对应的`modules.h`来include对应的模块的头文件，对应的`.c`文件夹就是`modules/` |


### 5.3 `include/rendezvos/` 与 `kernel/` 的子文件夹的对齐

头文件按`kernel/`下的内容分子目录，实现大体同名落在 `kernel/`：

| 公开头（示例） | 实现目录 | 具体内容 |
|----------------|----------|--------|
| `rendezvos/mm/*` | `kernel/mm/` | 内存 |
| `rendezvos/task/*` | `kernel/task/` | 线程与调度 |
| `rendezvos/ipc/*` | `kernel/ipc/` | IPC |
| `rendezvos/trap/*` | `kernel/trap/` | 陷阱分发 |
| `rendezvos/smp/*` | `kernel/smp/` | SMP 辅助 |
| `rendezvos/sync/*` | 主要实现锁和屏障，原子等部分在 `arch/<isa>/`） | 锁与屏障 |
| `rendezvos/registry/*` | `kernel/registry/` | 名称索引 |
| `rendezvos/system/*` | `kernel/system/` | panic / 关机 |
| `rendezvos/error.h` 等其他`include/rendezvos/`下的头文件 | 这也是内核到处公用的一些头文件 | 错误码等 |

### 5.4 `arch/` 与 `modules/`和对应的include文件夹

- **`arch/<isa>/`**：每个支持的 ISA 下通常有 `boot/`、`mm/`、`trap/`、`task/`、`smp/`、`time/` 等。v0.1 主要支持的是是 **x86_64** 与 **aarch64**；riscv64 / loongarch 有部分目录骨架和基本的代码，但完成度不同（见 §8）。选 `ARCH` 等于换整棵 arch 树、链接脚本和一批编译宏，而不是只改一个 `-D`（构建细节见 `01-构建与链接.md`）。  
- **`modules/`**：UART、日志、DTB/ACPI、ELF 辅助、PCI、测例、helloworld 等。通过配置决定编不编进来。

## 8. 多架构在布局上的含义

内核的整体逻辑架构（§4）跨 ISA 共用；**布局上**通过 `ARCH` 选出：

- 工具链与 `script/config/config_<isa>.json`  
- `script/link/<isa>_linker.ld`  
- `arch/<isa>/` 与 `include/arch/<isa>/`  
- 一批架构宏（如 `_X86_64_` / `_AARCH64_`），让公开头间接包含正确的 arch 头  

riscv64 / loongarch：目录在，不作与主线同等完成度的端口。多数公开 API 名称跨架构一致；差异集中在页表、trap 帧、IPI/TLB 等，由各专篇的「多架构」节（若存在）说明。

## 9. 测试在布局中的位置

core 自带测例在 `modules/test/`，由编译开关启用，主要验证的是 §4 里的RendezvOS core的设计，而非兼容层的 Linux（或其它 OS）测例。可在 core 树内独立跑；集成镜像里常关掉 core 自测、改跑兼容层测例（约定见 `01-构建与链接.md` §9）。清单与框架行为见 `43-内核测试框架与测例索引.md`。
