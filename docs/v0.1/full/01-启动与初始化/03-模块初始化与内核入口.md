v0.1 · 2026-09-25

## 1. 概述

启动总览里，最先起来的核叫 BSP，其余核叫 AP。到本核调用 `do_init_call` 的时候，这一核上该有的基本支持已经齐了：内存、陷阱（trap）入口、空的全局 port 表、boot 和 idle 线程、调度器等。正在执行 `do_init_call` 的，就是本核的 boot 线程。

兼容层若要在**启动顺序**上挂进来，走的就是这一步，而且只走 initcall——总览里另外两种注入方式不参与这条顺序。兼容层的构建脚本需要会把 `DEFINE_INIT` 的 `.o` 经 `EXTRA_OBJECTS` 链进同一个文件；`cmain` 里不会出现兼容层函数的名字，而是通过initcall来启动这些。

每个核只调用一次 `do_init_call`。BSP 在 `start_smp`（唤醒 AP）之前做完；AP 要等自己被拉起来、并且 `all_enabled`（BSP 宣布该尝试拉起的核都尝试过唤醒）之后才做，所以 BSP 的 `do_init_call` 一定先于任何一个 AP。这样排，是为了让 AP 上的初始化可以依赖 BSP 已经做过的全局initcall的工作，而不会和 BSP 交叉。函数若只该在 BSP、或只该在某个指定核上做事，需要自己看当前核编号是否符合预期，并在不符合预期的核上直接返回，`cmain` 不会替它跳过，也没有机制来指定某个initcall在某个核心上执行。

## 2. 目标与边界

本篇要说清楚三件事：init 表按 level 怎么排、怎么跑；跑的时候环境里已经有什么、还没有什么；以及「initcall里面兼容层生成server线程时，把线程放进调度器」和「server线程真正开始跑」不是同一时刻。

不在这里规定兼容层必须有哪些 server。

`do_init_call` 本身是同步的：表上的函数在 boot 线程里一个接一个返回，然后 BSP 才会去做后续工作，并进入 `kernel_handle_msg` 最终自旋等消息。

函数里如果调用了 `gen_thread_from_func`（也是兼容层常见的生成server内核线程的做法），只是把线程结构挂进本核调度器；入口函数此刻并没有在跑。要等 boot 进了收消息循环、调度选中它，那个 server 才真正执行。这就是总览里说的「注册 ≠ 运行」。

---

## 3. 分层与调用方

core 自己也可以用 `DEFINE_INIT` 挂模块，调用时本核的 `percpu(core_tm)`、`global_port_table`、`kallocator` 都已经就绪。和兼容层同样的，只该在 BSP 或某个指定核上做的事，在initcall调用的函数里判断 `percpu(cpu_number)`是否符合目标核心。

链接方把产品侧的 init 放进更小的 level（常见是 `DEFINE_INIT_LEVEL(..., 0)`），再经 `EXTRA_OBJECTS` 链进来。

注意 `cmain` 中 boot线程上需要接收处理消息，用 `kernel_set_ipc_handler` 登记一个函数指针，但那不是 initcall，只是一个回调。测例路径上的 `create_test_thread` 也不在initcall表里。

## 4. 数据结构与不变量

### 4.1 init 表

```c
typedef struct {
        void (*init_func_ptr)(void);
} Init_Info;

#define DEFINE_INIT_LEVEL(func_ptr, level) /* .init.call.<level> */
#define DEFINE_INIT(func_ptr)              /* level 固定为 3 */
static inline void do_init_call(void);     /* 扫 _s_init … _e_init */
```

链接脚本用 `_s_init` 到 `_e_init` 包住 `.init.call.0` 到 `.init.call.9`，以及一段 `.init.call`。`do_init_call` 从前往后线性调用这些函数。

函数没有参数，也没有约定返回值；失败只能自己打印或 panic，`cmain` 看不到返回码。

level 数字小的先跑。同一 level 里谁先谁后，等于这些 `.o` 被链进去的先后，没有别的顺序，通常也不能依赖编译顺序，如果需要更早的顺序，就放到更小的level。

### 4.2 调用时已经有什么、还没有什么

**已经有的：**

本核 `kallocator`、本核 `core_tm`、空的 `global_port_table`、本核CPU状态已就绪等其他可以正常启动线程的必要准备。

**还没有的：**

`"kernel_port"`——整张表跑完之后，才由 BSP 创建，这个port是让 boot 线程最后 `kernel_handle_msg` 收消息用的；

SMP 启动——在 BSP 上，initcall表的各个函数启动是在 `start_smp` 之前跑的，目标就是不和 AP 的initcall交错。

**其他**

每个核都会扫到表上的每一个函数，各调用一次。只该有一份的资源，要在函数里看当前是不是 BSP、或者是不是某个指定核。core 里的例子是 `powerd_init`：`percpu(cpu_number) != BSP_ID` 就返回；否则 `gen_thread_from_func` 生成一个名为 `"powerd"` 的线程，线程的具体执行里再创建并登记 `"powerd"` port。每核一份的 init 则在每个核上各建线程，但同一个 port 名不能登记两次。

## 6. 流程

### 6.1 BSP 上这一段怎么接

`init_proc` 返回（已经是 boot 线程）之后，`cmain` 依次做：`do_init_call` → `kernel_port_register` → `start_smp` → 可选的测例线程 → `kernel_handle_msg`。

`kernel_port_register` 在表跑完之后创建 `"kernel_port"`。`kernel_handle_msg` 查找这个port名字，然后循环试图从这个port进行 `recv_msg`。如果已经通过 `kernel_set_ipc_handler` 设了 handler，就把消息连同引用交给链接方；否则自己 `ref_put` 丢掉消息引用。查找失败（没有这个port）会返回错误，`cmain` 会请求关机；循环本身不返回。多个核的 boot 都会来收同一个 port，core 不在这里做排队仲裁（也就是可能在任何一个核心上收到发给这个port的消息，假定每个核心可以同构的处理）。

### 6.2 `powerd`：按核编号进行server启动的例子

`powerd_init` 先看 `cpu_number` 是不是 `BSP_ID`，做了初步环境检查之后，然后 `gen_thread_from_func(..., "powerd", ...)`，失败只打印。线程体里怎么建 port、怎么处理关机消息，直接看 `kernel/system/powerd.c`，本篇不展开。

## 7. 公开 API

本篇拥有两类接口：**initcall 表**（`include/rendezvos/task/initcall.h`）与 **boot 口 `"kernel_port"`**（声明在 `include/rendezvos/task/thread.h`，实现 `kernel/task/thread_boot.c`）。

`init_proc` / `gen_thread_from_func` 见线程专篇 §7。`rendezvos_request_poweroff` / panic 见 `40-错误码与panic.md` §7（本篇只把 `powerd_init` 当 DEFINE_INIT 按照不同核心进行启动的例子）。

### 7.1 编排顺序（调用方必须遵守）

| 路径 | 顺序（与源码一致） |
|------|-------------------|
| BSP（`cmain`） | `init_proc` → **`do_init_call`** → **`kernel_port_register`** → `start_smp` → … → **`kernel_handle_msg`** |
| AP（`start_secondary_cpu`） | （可选 `HELLO`）→ … → `all_enabled` 之后 → **`do_init_call`** →（可选 `RENDEZVOS_TEST`）→ **`kernel_handle_msg`**（**不**再 `kernel_port_register`） |
| handler | **`kernel_set_ipc_handler`** 须在消息到达前设好（通常放在某条兼容层的 `DEFINE_INIT` 里设定好了）；可传 `NULL` 表示丢弃消息 |

### 7.2 initcall（`initcall.h`）

类型、宏与链接段见 §4.1。这里只列调用约定。

| 接口 | 说明 |
|------|------|
| `DEFINE_INIT_LEVEL(f, level)` | 把 `f`（`void (*)(void)` 标识符）放进 `.init.call.<level>`。`level` 取 0–9，数字小的先跑；同 level 内次序=链接进 `.o` 的次序。函数无参、无返回码给 `do_init_call`；失败只能自己打日志 / panic。 |
| `DEFINE_INIT(f)` | 固定 level 3 的快捷写法。 |
| `do_init_call()` | 从 `_s_init` 扫到 `_e_init`，同步调用每一个入口。每个会跑到 `do_init_call` 的核都会各扫一整表；只该做一次的事必须在函数内看 `percpu(cpu_number)`（如例子 `powerd_init`）。在 boot 线程上同步返回；`gen_thread_from_func` 只挂调度器，**不等于**入口已在跑（「注册 ≠ 运行」）。 |

### 7.3 `"kernel_port"` 与 boot 收消息（`thread.h`）

```c
#define KERNEL_PORT_NAME "kernel_port"
typedef void (*boot_thread_ipc_handler_fn)(Message_t *msg, u16 service_id);
void kernel_set_ipc_handler(boot_thread_ipc_handler_fn handler);
error_t kernel_port_register(void);
error_t kernel_handle_msg(void);
```

| 接口 | 说明 |
|------|------|
| `KERNEL_PORT_NAME` | 字符串 `"kernel_port"`。 |
| `kernel_set_ipc_handler(h)` | 安装 boot 侧回调；`h == NULL` 时收到消息只 `ref_put`。不是 initcall。 |
| `kernel_port_register()` | `create_message_port` + `register_port`；成功则 `ref_put` 创建的引用，而让表持有引用。返回 `REND_SUCCESS` 或负 `error_t`。约定**仅 BSP、且在 `do_init_call` 之后**调用，函数体**不**检查 `cpu_number`，而是全局只有一个port；AP 再调会因重名注册失败（所以不调用）。 |
| `kernel_handle_msg()` | 查找`"kernel_port"`，失败则返回 `-E_RENDEZVOS`；成功则死循环 `recv_msg`，不返回。`recv_msg` 失败只打日志并 `continue`。有 handler 则把消息引用交给它（由 handler 负责 `ref_put`）；无 handler 则本函数丢掉引用。BSP 与各 AP 的 boot 都会进同一 port，core **不**做排队仲裁。 |

### 7.4 本篇顺带覆盖的其他内容

| 接口 | 说明 |
|------|------|
| `hello_world()`（`modules/helloworld`） | 条件要求`#ifdef HELLO`宏被定义，否则不生效（推荐还是开启）；BSP 在 `cmain`（`log_init` 后、`prepare_arch` 前）；AP 在 `start_secondary_cpu` 早期。**不进** init 表。 |

## 9. 测试

在 `core/` 里：`make ARCH=x86_64 config && make all && make run`（或 aarch64）。理论上正常跑完测例能够关机就行，因为initcall会启动powerd，然后在powerd里面正常关机，就说明initcall是正常的。

## 10. 限制与后续

同 level 没有稳定顺序，也没有「A 必须在 B 之后」的运行时检查。

函数不能向 `cmain` 报告失败。

只该在 BSP 或某个核上做的事，若函数不看当前核，就会在别的核上再做一份。
