# 模块初始化与内核入口

v0.1 · 2026-09-25

本篇覆盖：`include/rendezvos/task/initcall.h`、`kernel/task/thread_boot.c`（`"kernel_port"` 与 handler）、`kernel/system/powerd.c`、`modules/helloworld/helloworld.c`、`include/modules/helloworld/helloworld.h`。`cmain` 何时调用 `do_init_call` 见 `02-启动流程总览.md`。boot / idle 怎么切回来见 `03-任务与调度/13-线程与Task_Manager.md`。port 表见 `04-IPC/18-Port与消息模型.md`。每个核各自何时调用一次 `do_init_call`，见 `06-SMP与同步/28-SMP启动与处理器拓扑.md`。

## 1. 概述

到 `do_init_call` 被叫起来的时候，本核上该有的骨架已经齐了：内存、trap、空的全局 port 表、boot 和 idle。当前这条执行流就是本核的 boot 线程。

兼容层若要在**启动顺序**上挂进来，走的就是这一步，而且只走 initcall——总览里另外两种注入方式不参与这条顺序。做法是把带 `DEFINE_INIT` 的 `.o` 经 `EXTRA_OBJECTS` 链进同一张表；`cmain` 里不会出现兼容层函数的名字。

每个核只调用一次 `do_init_call`。BSP 这一次在 `start_smp` 之前做完，AP 这一次要等自己被拉起来之后才做，所以 BSP 一定先于任何一个 AP。这样排，是为了让 AP 上的初始化可以依赖 BSP 已经做过的全局工作，而不会和 BSP 交叉。函数若只该在 BSP、或只该在某个指定核上做事，自己看当前核编号，别的核直接返回——`cmain` 不会替它跳过。

---

## 2. 目标与边界

本篇要说清楚三件事：init 表按 level 怎么排、怎么跑；跑的时候环境里已经有什么、还没有什么；以及「把线程放进调度环」和「线程真正开始跑」不是同一时刻。

不在这里规定兼容层必须有哪些 server，也不再把 `init_proc` 的切换过程写一遍（见线程篇），更不展开 AP 等 `all_enabled` 的自旋（见 SMP 篇）。

`do_init_call` 本身是同步的：表上的函数在 boot 线程里一个接一个返回，然后 BSP 才会去登记 `"kernel_port"`、启 SMP、进入 `kernel_handle_msg`。函数里如果调用了 `gen_thread_from_func`，只是把线程结构挂进本核调度环；入口函数此刻并没有在跑。要等 boot 进了收消息循环、调度选中它，那个 server 才真正执行。这就是总览里说的「注册 ≠ 运行」。反过来，如果 init 函数自己就把 server 入口跑完再返回，boot 会被堵在这里，后面的 SMP 和收消息循环都走不到。

---

## 3. 分层与调用方

core 自己也可以用 `DEFINE_INIT` 挂模块，调用时本核的 `percpu(core_tm)`、`global_port_table`、`kallocator` 都已经就绪。只该在 BSP 或某个指定核上做的事，在函数里判断 `percpu(cpu_number)`，不由 `cmain` 代劳。

链接方把产品侧的 init 放进更小的 level（常见是 `DEFINE_INIT_LEVEL(..., 0)`），再经 `EXTRA_OBJECTS` 链进来。boot 上若要处理消息，用 `kernel_set_ipc_handler` 登记一个函数指针——那不是 initcall，只是一个回调。

测例路径上的 `create_test_thread` 不在这张表里。集成构建若要关掉测例，用 `OVERRIDE_CFLAGS` 卸掉 `RENDEZVOS_TEST`（见构建篇）。

## 4. 数据结构与不变量

### 4.1 init 表

```c
typedef struct {
        void (*init_func_ptr)(void);
} Init_Info;

#define DEFINE_INIT_LEVEL(func_ptr, level) /* .init.call.<level> */
#define DEFINE_INIT(func_ptr)              /* level 固定为 3 */
```

链接脚本用 `_s_init` 到 `_e_init` 包住 `.init.call.0` 到 `.init.call.9`，后面再兜一段 `.init.call`。`do_init_call` 从前往后线性调用。函数没有参数，也没有约定返回值；失败只能自己打印或 panic，`cmain` 看不到返回码。

level 数字小的先跑。同一 level 里谁先谁后，等于这些 `.o` 被链进去的先后，没有别的依赖声明。

### 4.2 调用时已经有什么、还没有什么

已经有的：本核 `kallocator`、本核 `core_tm`（当前是 boot）、空的 `global_port_table`、本核 trap。

还没有的：`"kernel_port"`——整张表跑完之后，才由 BSP 创建；以及 SMP 完成——在 BSP 上，这张表是在 `start_smp` 之前跑的。所以 init 里可以 `register_port` 自己的 port，但不要假定 `"kernel_port"` 已经在表上，也不要在这一刻把线程绑到还没被拉起来的核。

每个核都会扫到表上的每一个函数，各调用一次。只该有一份的资源，要在函数里看当前是不是 BSP、或者是不是某个指定核。core 里的例子是 `powerd_init`：`percpu(cpu_number) != BSP_ID` 就返回；否则 `gen_thread_from_func` 出一个名为 `"powerd"` 的线程，线程体里再创建并登记 `"powerd"` port。每核一份的 init 则在每个核上各建线程，但同一个 port 名不能登记两次。

## 6. 流程

### 6.1 BSP 上这一段怎么接

`init_proc` 返回（已经是 boot 线程）之后，`cmain` 依次做：`do_init_call` → `kernel_port_register` → `start_smp` → 可选的测例线程 → `kernel_handle_msg`。

`kernel_port_register` 在表跑完之后创建 `"kernel_port"`，`register_port` 进全局表，再 `ref_put`（表持有那份引用）。`kernel_handle_msg` 查找这个名字，然后循环 `recv_msg`。已经设了 handler，就把消息连同引用交给链接方；否则自己 `ref_put` 丢掉。查找失败返回错误，`cmain` 会请求关机；循环本身不返回。多个核的 boot 都会来收同一个 port，core 不在这里做排队仲裁。

### 6.2 `powerd`：按核编号门控的例子

`powerd_init` 先看 `cpu_number` 是不是 `BSP_ID`，再看 `core_tm` 在不在，然后 `gen_thread_from_func(..., "powerd", ...)`。失败只打印。线程体里怎么建 port、怎么处理关机消息，直接看 `kernel/system/powerd.c`，本篇不展开。

### 6.3 两条不走 initcall 的旁路

`HELLO` 下 `hello_world()` **不进** `.init.call`：BSP 在 `cmain` 的 `log_init` 之后、`prepare_arch` 之前调用；AP 在 `start_secondary_cpu` 很早（`arch_enable_percpu` 之前）也会再调一次。`RENDEZVOS_TEST` 也跟这张表无关：BSP 在 `start_smp` 之后 `create_test_thread(true)`，仍进入 `kernel_handle_msg`（boot 在 `recv_msg` 上阻塞，测例由 RR 调度）；AP 在 `do_init_call` 之后 `create_test_thread(false)`，再进收消息循环。

## 7. 公开 API

本篇拥有两类接口：**initcall 表**（`include/rendezvos/task/initcall.h`）与 **boot 口 `"kernel_port"`**（声明在 `include/rendezvos/task/thread.h`，实现 `kernel/task/thread_boot.c`）。说明与上述头文件注释一致，并已与 `.c` / 链接脚本核对。

`init_proc` / `gen_thread_from_func` 见线程专篇 §7。`rendezvos_request_poweroff` / panic 见 `40-错误码与panic.md` §7（本篇只把 `powerd_init` 当 DEFINE_INIT 门控例子）。

### 7.1 编排顺序（调用方必须遵守）

| 路径 | 顺序（与源码一致） |
|------|-------------------|
| BSP（`cmain`） | `init_proc` → **`do_init_call`** → **`kernel_port_register`** → `start_smp` → … → **`kernel_handle_msg`** |
| AP（`start_secondary_cpu`） | （可选 `HELLO`）→ … → `all_enabled` 之后 → **`do_init_call`** →（可选 `RENDEZVOS_TEST`）→ **`kernel_handle_msg`**（**不**再 `kernel_port_register`） |
| handler | **`kernel_set_ipc_handler`** 须在消息到达前设好（常见：某条 `DEFINE_INIT` 里）；可传 `NULL` 表示丢弃消息 |

### 7.2 initcall（`initcall.h`）

```c
typedef struct { void (*init_func_ptr)(void); } Init_Info;
#define DEFINE_INIT_LEVEL(func_ptr, level)  /* → .init.call.<level> */
#define DEFINE_INIT(func_ptr)               /* 等价 level == 3 */
static inline void do_init_call(void);
```

| 接口 | 说明 |
|------|------|
| `DEFINE_INIT_LEVEL(f, level)` | 把 `f`（`void (*)(void)` 标识符）放进 `.init.call.<level>`。`level` 取 0–9，**数字小的先跑**；同 level 内次序=链接进 `.o` 的次序，无依赖声明。函数无参、无返回码给 `do_init_call`；失败只能自己打日志 / panic。 |
| `DEFINE_INIT(f)` | 固定 level 3 的快捷写法。 |
| `do_init_call()` | 从 `_s_init` 扫到 `_e_init`，同步调用每一个入口。每个会跑到 `do_init_call` 的核都会**各扫一整表**；只该做一次的事必须在函数内看 `percpu(cpu_number)`（如 `powerd_init`）。在 boot 线程上同步返回；`gen_thread_from_func` 只挂调度环，**不等于**入口已在跑（「注册 ≠ 运行」）。 |

链接边界：`script/link/<isa>_linker.ld` 中 `_s_init` … `.init.call.0`–`.9` … `.init.call` … `_e_init`。

### 7.3 `"kernel_port"` 与 boot 收消息（`thread.h`）

```c
#define KERNEL_PORT_NAME "kernel_port"
typedef void (*boot_thread_ipc_handler_fn)(Message_t *msg, u16 service_id);
void kernel_set_ipc_handler(boot_thread_ipc_handler_fn handler);
error_t kernel_port_register(void);
error_t kernel_handle_msg(void);
```

| 接口 | 说明 |
|------|------|
| `KERNEL_PORT_NAME` | 字面量 `"kernel_port"`。 |
| `kernel_set_ipc_handler(h)` | 安装 / 替换 boot 侧回调；`h == NULL` 时收到消息只 `ref_put`。不是 initcall。 |
| `kernel_port_register()` | `create_message_port` + `register_port`；成功则 `ref_put` 本地引用（表持有剩余引用）。返回 `REND_SUCCESS` 或负 `error_t`。约定**仅 BSP、且在 `do_init_call` 之后**调用——函数体**不**检查 `cpu_number`；AP 再调会因重名注册失败。 |
| `kernel_handle_msg()` | `thread_lookup_port` 失败则返回 `-E_RENDEZVOS`；成功则 `for (;;)` `recv_msg`，**不返回**。`recv_msg` 失败只打日志并 `continue`。有 handler 则交出消息引用，否则丢掉。BSP 与各 AP 的 boot 都会进同一 port，core **不**做排队仲裁。 |

### 7.4 旁路（非 initcall，本篇顺带覆盖）

| 接口 | 说明 |
|------|------|
| `hello_world()`（`modules/helloworld`） | `#ifdef HELLO`：BSP 在 `cmain`（`log_init` 后、`prepare_arch` 前）；AP 在 `start_secondary_cpu` 早期。**不进** init 表。 |

## 8. 多架构

`.init.call.0` 到 `.init.call.9` 在主线链接脚本里一致。`do_init_call` 本身跟 ISA 无关。boot 栈从哪来见虚拟内存篇：BSP 用链接栈，AP 用 `ap_boot_stack_ptr`。

## 10. 限制与后续

同 level 没有稳定顺序，也没有「A 必须在 B 之后」的运行时检查。函数不能向 `cmain` 报告失败。只该在 BSP 或某个核上做的事，若函数不看当前核，就会在别的核上再做一份。多个 boot 竞争同一个 `"kernel_port"` 时，core 不仲裁。
