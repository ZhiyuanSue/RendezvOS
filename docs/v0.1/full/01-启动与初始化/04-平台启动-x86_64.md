# 平台启动-x86_64

v0.1 · 2026-10-03

本篇对应的源码是：`arch/x86_64/boot/boot.S`、`gdt.c`、`start_arch.c`、`boot/smp.c`（只含把 AP 入口汇编拷到低地址、并发 SIPI 的架构侧），以及 `include/arch/x86_64/desc.h`、`boot/arch_setup.h`、`multiboot.h`、`multiboot2.h`。

下文把最先起来的核叫 **BSP**，其余核叫 **AP**；AP 那段入口汇编（`ap_start`）叫跳板。整机何时调用 `prepare_arch` 等四个架构函数，见启动总览；链接脚本见构建篇。内存图和 ACPI 根指针（RSDP）怎么被后面的代码用掉，见物理内存篇与 ACPI 篇。运行期中断见 APIC/PIC 篇。谁拷跳板、INIT 和 SIPI 发几次，见 SMP 篇——本篇只解释跳板为什么必须落在低 1 MiB。

建议的读法：若对「32 位进 64 位、GDT、页表级数」不熟，先看 §4.6，再回头看布局和流程；§6 按时间往下走，不必在流程里回头翻手册。

本篇要讲清三件事：汇编怎样把机器交到 `cmain`；全机只做一次的平台初始化；每个核都要跑的 `arch_start_core`。

---

## 1. 概述

装载器（QEMU/`-kernel`、或支持 Multiboot 的引导程序）按照 **Multiboot1 或 2** 把一份扁平的 `kernel.bin` 放到物理地址 `0x100000`，并在 **32 位保护模式、分页尚未打开** 时跳进 `bsp_entry`。这是协议规定的入口状态，不是我们自己挑的。链接脚本却把内核符号挂在高半虚拟地址 `0xffff800000100000` 上，所以汇编必须先让「低物理地址」和「高半虚地址」看见同一份镜像，再按手册顺序进入 64 位长模式，最后用一条绝对跳转落到链接地址，`call cmain`。

ACPI、PCI、每核中断控制器这类事情故意不塞进这段汇编：它们要么需要先读完内存图，要么需要内核堆。`prepare_arch` 只核对 magic、把命令行指针拿出来；内存图和 ACPI 根指针（RSDP）等到 `phy_mm_init`；有了堆之后 `arch_start_platform` 全机做一次 ACPI/PCI；每个核自己的段表、中断、系统调用入口和时钟放在 `arch_start_core`。

为什么不把 ELF 直接丢给 QEMU 当内核？它对「x86_64 ELF 当 `-kernel`」的支持并不完整，Multiboot 装扁平 bin 反而稳。UEFI 直启是另一套协议，本版本不做。相关讨论可见 [QEMU 邮件列表](https://lore.kernel.org/qemu-devel/20240206135231.234184-1-jens.nyberg@gmail.com/)、[PVH / ELF 加载的说明](https://stefano-garzarella.github.io/posts/2019-08-23-qemu-linux-kernel-pvh/) 和 [Xen PVH](https://xenbits.xen.org/docs/unstable/misc/pvh.html)；为启动去跟一整套新协议，目前没有必要。Multiboot1 规范在 [GNU GRUB 手册](https://www.gnu.org/software/grub/manual/multiboot/multiboot.html)。

（PS：QEMU 以后会不会补上 ELF 直启不好说，但启动路径跟着模拟器短期行为改来改去，不合适。）

## 2. 目标与边界

要讲清的是：Multiboot 头在 boot 里起什么作用；从 `bsp_entry` 到 `cmain` 期间页表和模式怎么切；`setup_info` 各字段谁写谁读；BSP 上的 `prepare_arch` / `arch_cpu_info` / `arch_start_platform`，以及每核的 `arch_start_core`，各自负责哪一段。

不在这里展开 IOAPIC/MSI 路由、ACPI 表逐字段、以及怎样并行唤醒多颗 AP。

---

## 3. 分层与调用方

`boot.S` 只对装载器负责，成功就进 `cmain`，没有 C 调用方。<br>进了 C 之后，`start_arch.c` 里那四个与 aarch64 同名的函数由 `cmain`（AP 上则是 `start_secondary_cpu`）按固定顺序调用，这样总览那一层不必按 ISA 分叉。

以后若改成别的引导协议，改的是本篇的头和 `boot.S`，不是 `cmain` 的编排。

## 4. 数据结构与不变量

硬件上的名词（模式、段表、页表为什么是第 256 项、MSR 是什么）集中在 **§4.6**。下面 4.1–4.5 讲本实现怎么摆数据和怎么走步骤；读到不明的缩写可以先翻 4.6（当然，如果有条件，强烈建议读一遍Intel或者AMD相关手册，并长期备在手边）。

### 4.1 `struct setup_info`（x86_64）

这是 `boot.S` 留给后面整条 C 启动链的一块状态，定义在 `include/arch/x86_64/boot/arch_setup.h`，汇编 `.boot.data` 里有同名符号，C 头和汇编里的字段顺序、大小必须对得上。前半是 x86 专用字段；末尾 `ap_boot_stack_ptr` 和 `cpu_id` 与别的 ISA 对齐，语义见启动总览 §4.1.1，这里只给本架构的偏移。

| 偏移 | 字段 | 谁写 | 谁读 / 用途 |
|------|------|------|-------------|
| `0x0` | `multiboot_magic` | `bsp_entry`（`eax`） | `prepare_arch` 用来区分 Multiboot1（`0x2BADB002`）和 2（`0x36d76289`） |
| `0x4` | `multiboot_info_struct_ptr` | `bsp_entry`（`ebx`，物理地址） | 经 GET 宏加上高半偏移后，读内存图、命令行等 |
| `0x8` | `phy_addr_width` | `bsp_entry`（`CPUID（EAX=0x80000008）` 的 AL） | `prepare_arch` 抄到全局 `max_phy_addr_width` |
| `0xc` | `vir_addr_width` | 同上（AH） | 存下来；后面主要用物理宽度 |
| `0x10` | `rsdp_addr` | `arch_init_pmm`（进 `cmain` 时还是 0） | `arch_start_platform` 拿去 `acpi_init` |
| `0x18` | `ap_boot_stack_ptr` | `arch_start_smp`（发 SIPI 前） | 见总览 §4.1.1 |
| `0x20` | `cpu_id` | `arch_start_smp`（发 SIPI 前） | 见总览 §4.1.1 |

已经跑在高半之后，C 代码不能直接解引用那根**物理** info 指针，必须走 `GET_MULTIBOOT_INFO` / `GET_MULTIBOOT2_INFO`，把物理地址加上 `KERNEL_VIRT_OFFSET`。

RSDP 是 ACPI 表的入口指针。不在 `prepare_arch` 里找，是因为扫内存图、给 ACPI 占用的区域留空，本来就发生在物理内存初始化里；找到后写回这块 `setup_info`，平台钩子再读。

### 4.2 链接、加载与早期物理布局

链接脚本（`script/link/x86_64_linker.ld`）约定：高半窗口 `kernel_virt_offset = 0xffff800000000000`，加载偏移 `kernel_start_offset = 0x100000`，所以符号从虚地址 `0xffff800000100000` 往上排。构建时 ELF 再被 `objcopy` 成 `kernel.bin`。Multiboot 头里的 load / bss / entry 写的是**物理**地址（链接符号减去高半偏移），装载器就按这些字段把镜像放到 PA `0x100000`。于是早期映射可以对齐成一句：

**高半虚地址 = 物理地址 + `kernel_virt_offset`**。加载点就是 `0xffff800000100000` 对着 `0x100000`。

```text
物理地址（装完之后）

  0x000000  实模式中断向量表
  0x001000  稍后拷 AP 跳板用的那一页（启动此刻镜像还不在这）
      …     BIOS / 低 1 MiB（留给固件和跳板，不进 buddy）
  0x100000  ← kernel.bin，也就是 BIOS_MEM_UPPER
            |  .text：Multiboot 头、boot.S、早期页表、内核代码
            |  .init / .rodata / .data
            |  .bss：boot 栈，栈顶符号 _boot_stack_bottom
            |  .percpu 模板
            |_end

早期虚拟窗口（同一段物理内核，两处都能看见；页表怎么挂见 §4.3）

  低址恒等    VA  0x00100000          ────────┐
                                             ├── 同一 PA 0x100000 起的镜像
  高半链接    VA  0xffff800000100000  ────────┘
```

早期页表页作为 `.boot.page` 链进 `.text`；boot 栈在 `.bss`。`phy_mm_init` 插入可用物理区时，也以 `0x100000` 为下限。

### 4.3 早期页表（四级，2 MiB 大页）

静态表放在 `.boot.page` 里。本仓库把四级叫做 L0–L3，对应手册的 PML4 / PDPT / PD / PT。为什么高半要用第 256 项、虚拟地址怎样才合法，§4.6 有一段专讲；这里只写这张表填了什么。

L0 的第 0 项和第 256 项都指向同一张 L1：前者覆盖低地址，开分页后还可以用物理地址附近的虚地址继续取指；后者对应高半 `0xffff8000…`。两扇门进同一张下一层表，所以同一份物理内核在低址窗口和高半窗口里都能取到。

L1 只填了第 0 项，指向 L2。内核从 1 MiB 起步，正常也到不了一整 GiB，一张 PDPT 项的范围够用。

L2 启动时全零。开分页之前，`bsp_entry` 按内核物理区间 `[_kstart, _end)` 每 2 MiB 写一项，标志是存在、可写、大页（`PS`）、全局（`G`）。`PS` 表示这就是 2 MiB 页，不再指向更下一层。不用 1 GiB 页，是因为不少 CPU 并不保证支持，而若干个 2 MiB 已经盖得住当前镜像；填多少项跟镜像实际上界走，不预先写满。

进入长模式后，执行流还在低地址那里，再靠 `movabs` 跳到链接高半。`bsp_entry` 进 `cmain` 时**不会**拆这张早期表：后面唤醒 AP 还要用低地址跳板。恒等窗口留到 `start_smp` 末尾，由 x86 的 `arch_start_smp` 调用 `clean_tmp_page_table` 再拆，见 SMP 篇。运行时页表由内存子系统另建，是另一条线。

### 4.4 进入 IA-32e 的硬件顺序

从 32 位保护模式进 64 位分页，手册规定的顺序不能乱：先在 `CR4` 里打开 PAE，再在 `EFER` 里打开长模式使能，把 L0 的物理地址装进 `CR3`，最后打开 `CR0` 的分页位。反了得不到合法的 64 位环境。这些寄存器各自管什么见 §4.6。

同一组宏里还会多开几位。它们不是「进长模式」的最低要求，但后面马上要用，与其再改一次 `EFER`/`CR4`，不如现在一起打开：

| 多开的位 | 若不开 | 本内核为什么现在就开 |
|----------|--------|----------------------|
| `CR4.PGE` | 页表上的全局位被忽略 | 早期 2 MiB 项写了全局位；以后换地址空间时，这些内核映射不必从 TLB 里整表刷掉 |
| `EFER.SCE` | `syscall` / `sysret` 是非法指令 | 每核稍后要登记系统调用入口，长模式一开就把门打开 |
| `EFER.NXE` | 页表上的「禁止执行」位无效 | 后面用户/内核页要做写与执行分离，现在开，之后填的位才算数 |

打开分页之后还要换代码段：临时 GDT 里只有空项和一条「64 位代码段」，`lgdt` 再 `ljmp` 进 `.boot_64` 的 `x86_64_entry`。临时表的作用仅限于让 CS 从 32 位变成 64 位译码；每核正式的表要等到 `arch_start_core`。

### 4.5 `BSP_ID` 与 percpu

C 代码起来之后，要给这颗启动核一个软件编号，并启用它的 per-CPU 区（用 GS 指向那一块，见 §4.6）。`arch_cpu_info` 用 `CPUID（EAX=1）` 读出 APIC ID，写进 `BSP_ID`；`cmain` 先做这一步，再 `arch_enable_percpu(BSP_ID)`，所以 GS 用的是改写后的编号。

这次 CPUID 只给出 **8 位** APIC ID，和「从 0 起稠密编号」不是同一套规则。以后若遇到稀疏或超过 8 位的拓扑，不能把这个值直接当槽号，见启动总览 §10。

### 4.6 启动用到的硬件基础

下面按「读本篇会碰到的顺序」讲，不必一次记完。中断如何路由、系统调用那几份 MSR 怎么填、per-CPU 变量怎么访问，分别在中断篇、系统调用入口篇、per-CPU 篇。

#### 工作方式：实模式、保护模式、长模式

同一颗 CPU 会换几种工作方式。**实模式**是 16 位，复位或 SIPI 之后 AP 停在这里，寻址还是段移位加偏移，没有页表，只有物理地址寻址。Multiboot 装载器会从实模式走一段，把 BSP 交到 **保护模式、分页关闭**（32 位），这才是 `bsp_entry` 的入口。历史上也有内核长期跑在 32 位保护模式甚至段页式上，本框架从一开始就按 64 位来，那些路径不介绍。目标状态是 **IA-32e 长模式**：64 位，地址靠四级页表翻译，`cmain` 以后的 C 都在这里。`boot.S` 要做的，就是在 32 位里建好早期页表，按规定打开长模式，再跳到高半虚地址。

进长模式时控制寄存器的顺序是固定的：先 `CR4.PAE`，再 `EFER.LME`，页表根写入 `CR3`，最后 `CR0.PG`。多开的位见 §4.4。

#### 特权级

CPU 还有当前特权级。内核跑在 **0**；**3** 是给以后非内核代码用的最低档。GDT 里标成 `dpl=3` 的项常叫「用户代码段/数据段」，意思只是「允许特权级 3 使用」，不是「现在已经有用户进程」。

#### 段表、CS 和 TSS

长模式并不靠段来做地址翻译（基址当 0，限长也不检查），但取指用的 **CS** 仍必须指向合法描述符，并且 **L=1、D=0**，CPU 才按 64 位指令译码。`lgdt` 告诉 CPU 表在哪，`ljmp` 把 CS 换成表里对应项（临时表里那条代码段的选择子是 `0x08`）。SS、DS 等也要指向合法项，否则会通用保护异常。**TSS**（任务状态段）在当代内核里几乎不用来做硬件任务切换，主要是中断时让 CPU 自动切到内核栈，细节见陷阱篇。

#### MSR

**MSR** 是一批用编号寻址的 64 位配置，`rdmsr` / `wrmsr` 读写。见到名字先当「有编号的配置位」即可。本篇会碰到 `EFER`（长模式、禁止执行、系统调用使能），以及 GS 的基址；系统调用那一组（跳到哪、进核清哪些标志）见系统调用篇。

#### GS 与本核数据

x86 习惯用 **GS** 指向本核私有数据。硬件给了两份基址：当前正在用的，以及一份藏着的、用一条对换指令和当前这份对调。内核跑着时，当前这份已由 `arch_enable_percpu` 写成 per-CPU 区；还没有低特权线程时，把藏着的那份清 0，免得对换读到垃圾。

#### `syscall` / `sysret`

低特权以后可以用 **`syscall` 进内核、`sysret` 返回**，不必走完整中断门。CPU 从 MSR 里取出跳转目标和两套 CS/SS。返回时按固定间隔取特权级 3 的数据段和代码段，所以 GDT 里必须数据段紧挨在代码段前面。`EFER.SCE` 只是打开这条指令，不开就会当成非法操作码。怎么填那些 MSR，见系统调用入口篇。

#### CPUID

**CPUID** 执行前把功能号放进 EAX（手册叫 leaf，本文写成 `CPUID（EAX=…）`），结果在 EAX/EBX/ECX/EDX。本篇用到：`EAX=0x80000001` 的 EDX bit 29 表示能否进长模式；`EAX=0x80000008` 给出物理/线性地址宽度；`EAX=1` 的 EBX 高 8 位是启动时的 APIC ID，本实现拿它当 `BSP_ID`（更大的 x2APIC 编号见中断篇）。`arch_cpu_info` 还会再问几次，采厂商串和 SSE 等能力。core 不扫完全部功能号。

#### 四级页表与第 256 项

长模式默认四级页表：手册叫 PML4 → PDPT → PD → PT，本仓库叫 L0…L3。虚拟地址高 16 位必须是规范形式（位 63…48 等于位 47 的符号扩展），`0xffff800000000000` 满足，所以能当高半窗口。PML4 下标来自 VA 的 \[47:39\]；`0xffff8000…` 这一段算出来是 256，所以静态表把第 256 项和第 0 项指到同一张下一层——这是硬件怎么切地址，不是随便选的槽。PD 上 PS=1 表示 2 MiB 大页；1 GiB 大页要 CPUID 声明支持，本实现不用。项上的全局位要 `CR4.PGE` 才生效。

#### 物理地址、虚地址和早期两处窗口

分页关闭时，CPU 看见的就是物理地址；打开之后先走虚地址再翻译。本篇早期让同一段物理内核出现在两处：**虚地址等于物理地址**（低址，为了刚打开分页时还能取指），以及 **虚地址等于物理地址加高半偏移**（链接地址）。装载器必须把 bin 放到 `0x100000`，链接脚本才对得上，见 §4.2。最低的 4 KiB 是实模式向量表；`0x1000` 留给 AP 跳板，因为 SIPI 只能从「页帧号 × 4 KiB」起步。低于 1 MiB 的内存不进 buddy。

#### SIPI 与 AP 跳板

AP 被 INIT 之后停在实模式。BSP 通过 Local APIC 发 **SIPI**，向量字段是起始页帧号，CPU 从那个物理页开始取指。所以跳板必须在低 1 MiB 且页对齐，本实现用 `0x1000`。发几次、谁拷贝，见 SMP 篇。

#### 浮点 / SIMD

长模式下默认去碰 SSE 一类指令可能异常。操作系统要在控制寄存器里声明自己接得住、保存得了状态，编译出来的 C 才能用。`arch_start_core` 按 CPUID 去开，失败只打日志。

#### Multiboot 装载约定

以上是 CPU 自己的模式和地址翻译。镜像怎么被放进内存、入口寄存器里是什么，走的是另一套装载约定，不是 Intel 手册里的一章。[Multiboot1](https://www.gnu.org/software/grub/manual/multiboot/multiboot.html) 规定入口 `EAX` 是 magic、`EBX` 是 information 结构的物理地址；头里若带了 address 字段，就按给定物理区间装扁平镜像。本镜像还嵌了一套 Multiboot2 头，`prepare_arch` 两种都认。

## 6. 流程

下面按时间走：装载器先看到镜像头，再进入 BSP 汇编，AP 只在这里点到跳板为止；进 C 之后是全机一次的架构函数，最后每核补自己的运行环境。总览里夹在中间的物理/虚拟内存初始化，本篇不重复。

### 6.1 Multiboot 头：为什么长成这样

镜像一开头先跳到真正的入口，紧跟着一块 Multiboot1 头：约定的 magic，以及「我需要内存信息」「我自己提供装载地址」两个标志。因为产物是 **bin 不是 ELF**，头里必须写出 header / load / load_end / bss_end / entry 的物理地址（一律用符号减去高半偏移）。同一文件里还有一套 Multiboot2 头，带地址 tag 和入口 tag，方便以后换只认 MB2 的装载器；运行时两种 magic 都认。

### 6.2 `bsp_entry`：从 32 位走到 `cmain`

进来时仍是 32 位、分页关着。`eax` 是 magic，`ebx` 是 information 结构的物理指针，两者马上写入 `setup_info` 开头。此刻指令指针还在物理低址，所以写内存时用的是「符号减去高半偏移」。

栈开在 `.bss` 里，所以设栈之前先从 `_bss_start` 按字节清到 `_bss_end`，再把栈指针设成 `_boot_stack_bottom` 的物理地址，并用 `push 0; popf` 清 flags。

接着问 CPU 能不能进长模式（`CPUID（EAX=0x80000001）` 的 EDX bit 29），不能就停住。再问地址宽度（`EAX=0x80000008`），写入 `setup_info`。功能号的含义见 §4.6。

然后按 §4.3 填 L2：下界对齐内核起始的物理地址，上界对齐结尾，每 2 MiB 一项。填完就按 §4.4 的顺序打开 PAE、长模式使能、装 CR3、开分页，加载临时段表并跳进 64 位入口。

64 位入口里，低址和高半已经映射同一份代码，于是用 `movabs` 跳到真正的链接地址，把数据段寄存器清掉，栈改成高半的 `_boot_stack_bottom`，把 `setup_info` 的高半指针放进调用约定的第一个参数，进入 `cmain`。如果 `cmain` 居然返回，就停在 `hlt`。

### 6.3 AP 入口（本篇只到跳板）

`.boot.ap_code` 里的 `ap_start` 是 16 位实模式入口，被拷到物理 `0x1000` 之后，SIPI 才能打中它。它自带一份进保护模式用的临时段表，打开保护模式后进 32 位，再走和 BSP 相同的「开分页、进长模式」，最后进入 `start_secondary_cpu`。谁拷贝跳板、谁写入栈顶和 `cpu_id`、谁发 INIT-SIPI，见 SMP 篇。

### 6.4 进 C 之后、全机只做一次的架构函数

`cmain` 会按总览里的顺序调用三个与 BSP/全机相关的架构函数，中间还夹着物理内存和虚拟内存初始化。这里只说这三个自己干什么。

`prepare_arch` 把物理地址宽度抄到全局变量，确认 magic 是 Multiboot1 或 2，若有命令行就把指针设好（Multiboot1 的命令行还是物理地址，要加上高半才能读）。它不扫内存图，也不找 RSDP，那两件事在 `phy_mm_init` → `arch_init_pmm`：只有超过 1 MiB 的可用区才进 buddy，找到的 RSDP 写回 `setup_info`。

`arch_cpu_info` 不用它的参数。它问若干次 CPUID，填全局 `cpu_info`（厂商、APIC ID、SSE 一类能力、地址宽度），再把 `BSP_ID` 设成 APIC ID。不追求把所有功能号问遍。

`arch_start_platform` 必须在虚拟内存和堆起来之后。它用 RSDP 初始化 ACPI，再用 BSP 的堆分配 PCI 根节点并扫描。失败把错误码交回 `cmain`。AP 不会进这个函数。

### 6.5 每个核：`arch_start_core(cpu_id)`

BSP 走到这里时由 `cmain` 调用，AP 则由 `start_secondary_cpu` 调用。汇编已经让这颗核跑在 64 位并能执行 C；本函数补的是**这一核自己还缺的运行环境**。下面用到的段表、GS、系统调用等，§4.6 有说明。这里仍然不创建线程或 port。

先换成每核正式段表。临时表只有一条 64 位代码段；正式表里还有内核数据段、TSS，以及两项特权级 3 的代码/数据段。后两项现在没有线程会用到，是给以后从内核返回到低特权代码准备的。系统调用返回时硬件按固定间隔取这两项，所以数据段必须排在代码段前面。寄存器里具体怎么写，见系统调用入口篇。

然后记下本核编号。内核正在用的那份 GS 基址，上一钩子 `arch_enable_percpu` 已经写成 per-CPU 区；还有一份给以后和低特权切换时对换的基址，现在先清 0。接着装本核 TSS。

再装本核中断向量表，并接上中断控制器（有 x2APIC 用 x2APIC，否则 xAPIC，再不行才用 8259；依赖平台阶段已经解析过 MADT）。软 IPI 和跨核刷 TLB 也在这里登记，细节见中断篇和 SMP 篇。

再告诉 CPU：低特权执行 `syscall` 时跳到哪段内核入口，进去时要清掉哪些标志（本实现会关掉可屏蔽中断）。

最后打开本核中断、起时钟。C 和编译器可能用到 SSE 一类指令，长模式下默认去碰会异常，所以按前面采到的 CPUID 打开操作系统侧的浮点支持。探测失败只打印，并不让这个函数失败。

## 7. 公开 API

本篇对外的 C 接口就是 `arch_setup.h` 里那四个与 ISA 同名的函数（实现都在 `start_arch.c`）。`boot.S` 的入口只有装载器和跳板会跳进去，没有另做公开头。`arch_start_smp` 归 SMP 篇，`arch_enable_percpu` 归 per-CPU 篇，从内存图里找 RSDP 归物理内存篇。

### 7.1 编排顺序（与源码一致）

| 调用方 | 和本篇有关的顺序 |
|--------|------------------|
| BSP `cmain` | … → **`prepare_arch`** → `phy_mm_init` → **`arch_cpu_info`** → `arch_enable_percpu(BSP_ID)` → `virt_mm_init` → **`arch_start_platform`** → **`arch_start_core(BSP_ID)`** → … |
| AP `start_secondary_cpu` | … → **`arch_start_core(cpu_id)`** → …（不再走 `prepare_arch` / `arch_cpu_info` / `arch_start_platform`） |

### 7.2 Multiboot 访问（布局见 §4.1）

字段表见 §4.1。这里只留 C 侧真正会调用的转换：

```c
struct multiboot_info  *GET_MULTIBOOT_INFO(struct setup_info *);
struct multiboot2_info *GET_MULTIBOOT2_INFO(struct setup_info *);
```

| 项 | 说明 |
|----|------|
| `GET_MULTIBOOT_*` | 把 info 的物理指针加上高半偏移，得到可以解引用的内核虚地址（分页已经打开之后） |
| `BIOS_MEM_UPPER` | `0x100000`，buddy 可用区下限 |
| Multiboot 结构体 | 协议字段在 `multiboot.h` / `multiboot2.h`，不当成本篇的调用 API 逐项展开 |

### 7.3 四个架构钩子（x86 侧语义）

```c
error_t prepare_arch(struct setup_info *arch_setup_info);
error_t arch_cpu_info(struct setup_info *arch_setup_info);
error_t arch_start_platform(struct setup_info *arch_setup_info);
error_t arch_start_core(cpu_id_t cpu_id);
```

| 接口 | 说明 |
|------|------|
| `prepare_arch` | 抄物理地址宽度；只认两种 Multiboot magic；可选设置命令行指针。不读内存图、不找 RSDP。成功返回 0；magic 不对返回 `-E_RENDEZVOS`，`cmain` 会 panic。 |
| `arch_cpu_info` | 参数不用。填 `cpu_info`，`BSP_ID = APIC ID`。总是成功。 |
| `arch_start_platform` | 全机一次，须在虚拟内存之后。ACPI 然后 PCI 扫描。把错误码交回。AP 不得调用。 |
| `arch_start_core` | 每核一次，补中断、系统调用入口和 SIMD，顺序见 §6.5。总是返回 0；SIMD 失败只打日志。不建线程或 port。 |

### 7.4 本篇有源码、但不算本篇公开 API 的符号

| 符号 | 归属 |
|------|------|
| `bsp_entry` / `x86_64_entry` / `ap_start` | 装载器或 SIPI 跳入，没有 C 声明头 |
| `arch_start_smp` | SMP 篇 |
| GDT 下标 | `arch_start_core` 内部；系统调用入口篇说明返回低特权时为什么要这个顺序 |

---

## 8. 多架构

这些是 x86_64 自己的启动细节。和 aarch64 相比，差别主要在引导协议（Multiboot 加 BIOS 区里的 RSDP，而不是 Image 加设备树）、`BSP_ID` 来自 APIC ID 而不是写死 0、以及 AP 需要低地址 16 位跳板。相同的是交给 `cmain` 的四个函数名字和参数。
