# 内核测试框架与测试用例索引

v0.1 · 2026-09-27

本篇覆盖：`modules/test/test.c`、`single_test.c`、`smp_test.c`、`include/modules/test/test.h` 及各 `single_*` / `smp_*` / `thread_affinity_test.c`。

开关 `RENDEZVOS_TEST` 见构建篇（`01`）；关机见 `40`。这里验证的是 **core 原语**，不是兼容层系统调用的回归。

---

## 1. 概述

启用后：

| 角色 | 行为 |
|------|------|
| **BSP**（Bootstrap Processor，启动处理器） | `BSP_test` 跑 `single_cpu_test` + `multi_cpu_test`，常以 **`rendezvos_request_poweroff`** 收尾 |
| **AP**（Application Processor，应用处理器） | 只执行 `multi_cpu_test` |

两张**静态表**驱动，没有构造器 / linker section 自动注册。加测试用例 = 改表。

框架分层与分发：

```text
   cmain (BSP)                         start_secondary_cpu (AP)
      │                                    │
      ▼                                    ▼
   create_test_thread(true)            create_test_thread(false)
      │                                    │
      ▼                                    ▼
   BSP_test                            AP_test
   ┌──────────────┐                    ┌──────────────┐
   │ single_cpu_   │→ 顺序执行 single_test[]  │ (跳过)      │
   │ test          │                    │              │
   ├──────────────┤                    ├──────────────┤
   │ multi_cpu_    │→ 各核并行 smp_test[]  │ multi_cpu_   │→ 同步执行 smp_test[]
   │ test          │   BSP 做 barrier      │ test         │   等 curr_test 推进
   └──────┬───────┘                    └──────┬───────┘
          ▼                                   ▼
   rendezvos_request_poweroff            schedule (循环)
          │
          ▼
   schedule
```

| 表 | 行为 |
|----|------|
| `single_test[]` | BSP 顺序执行；返回值 0=pass，非 0=fail（多用 `-E_REND_TEST`） |
| `smp_test[]` | 各核并行同一 case；BSP 做 barrier（内含 `schedule`）；若提供 `check_result()` 则 **忽略**每核返回值，只信 BSP 汇总 |

槽上限 `MAX_SINGLE_TEST_CASE = MAX_SMP_TEST_CASE = 10`。single 实占 9 槽（`pmm_test` 注释掉）、smp 实占 8 槽（`smp_log_test` 注释掉）——再加测试用例需数一数已用槽位。

## 2. 目标与边界

**提供：** 表驱动框架；barrier；按域索引。
**不做：** 自动发现；失败时整机一致优雅退出（见 §6）；兼容层 / 用户态回归。

`pmm_test` 在 single 表里 **注释掉**（会耗尽物理帧）。`smp_log_test` 常注释（只看输出）。

---

## 3. 分层与调用方

- BSP：`kernel/system/main.c` 的 `cmain` 调 `create_test_thread(true)`。
- AP：`kernel/smp/smp.c` 的 `start_secondary_cpu` 调 `create_test_thread(false)`。
- `RENDEZVOS_TEST` 是双保险：调用点（`main.c` / `smp.c`）包在 `#ifdef` 里，`BSP_test` / `AP_test` **函数体内再包一层**——即使宏没开而线程被创建，函数体也只剩 `schedule`。
- 禁用：`OVERRIDE_CFLAGS=-URENDEZVOS_TEST` 或关 json feature。
- 注册：改 `single_test[]` / `smp_test[]`；测试用例线程名固定 `test_thread`，挂在各自核的 `core_tm` 上。

测试用例线程与 boot IPC 循环 **非互斥**（boot 仍进入 `kernel_handle_msg`，在 `recv_msg` 上阻塞；调度器只选 `ready`，故不会再选中已阻塞的 boot）。

## 4. 数据结构：测试用例表怎么描述一条 case

框架很薄：开机后 BSP 顺序跑单核表，再和各 AP 一起跑多核表（流程见 §6）。对象上就是两张静态表，每项说明「跑哪个函数、打印什么名字、多核时要不要只由引导核做总判定」。

```c
#define MAX_SINGLE_TEST_CASE 10
#define MAX_SMP_TEST_CASE    10

struct single_test_case {
        int (*test)(void);
        char name[32];
};

struct smp_test_case {
        int (*test)(void);
        char name[32];
        bool (*check_result)(void);
};
```

| 字段 | 为什么要有 |
|------|-----------|
| `test` | 真正执行的测试用例函数。约定：**返回 0 = 通过，非 0 = 失败**。 |
| `name` | 打印用（`[ SINGLE CPU TEST xxx ]` 一类）。 |
| `check_result`（仅 SMP） | 可选。为 NULL 时：每个 CPU 的 `test()` 返回值都计入，任一非 0 即失败。非 NULL 时：各核仍跑 `test()`，但**只信 BSP 调 `check_result()` 的布尔结果**（适合「多核一起改共享状态、最后由 BSP 看一眼」的 case）。 |

运行时还有两颗跨核同步量（不在上述结构体里，在 `smp_test.c`）：

| 量 | 为什么要有 |
|----|-----------|
| `curr_test`（`volatile u64`） | 当前 SMP case 号，**只由 BSP 推进**（汇总通过才 `curr_test++`）；AP 自旋等到自己该跑的下标。 |
| `test_state[]`（`volatile` 状态枚举，长 `RENDEZVOS_MAX_CPU_NUMBER`） | 每核记录的是**状态**而非原始返回值：`not_start / running / success / fail`。无 `check_result` 时按 `test()` 返回值标 `success`/`fail`；有 `check_result` 时各核一律标 `success`（返回值被忽略）。 |

`NR_CPU`：同步循环扫 `0..NR_CPU-1`，等于假设 `cpu_id` 从 0 起稠密编号——这在 aarch64 上恒成立；x86_64 上 `cpu_id` 直接取 APIC id、可能跳号，`NR_CPU` 只是条目个数，与「最大 `cpu_id`+1」不是一回事（SMP 篇（`28`）§4.2），所以该假设只在 APIC id 恰好从 0 连续时成立。

## 6. 流程与失败注意

```text
BSP: single 顺序 → smp 各 case → request_poweroff → schedule
AP:  等 curr_test → 执行 smp case → …
```

### 6.1 SMP 测试 case 同步与 check_result 判定

框架里**没有**现成的 `barrier()` 原语——所谓 barrier 是两段自旋循环（`arch_cpu_relax()` + `schedule()` 让出）加 `curr_test` 计数器的组合。所有核跑同一个 `multi_cpu_test`，只在收尾处按 `cpu_id == BSP_ID` 分叉：

```text
multi_cpu_test 主循环（每核都执行；j 遍历 0..NR_CPU-1）：
  for (i = 0; i < MAX_SMP_TEST_CASE; i++) {
      if (smp_test[i].test == NULL) break;         // SMP 表遇空槽即停
      test_state[cpu] = running;
      // 起跑 barrier：等所有 test_state[j] 都不再是 not_start
      while (curr_test == i) { if (无 j 仍为 not_start) break; relax; schedule; }
      if (smp_test[i].check_result == NULL)
          test_state[cpu] = test() ? fail : success;   // 返回值计入
      else {
          test();
          test_state[cpu] = success;                   // 返回值一律忽略
      }
      if (cpu == BSP) {
          // 收尾 barrier：等所有 test_state[j] 都不再是 running
          ok = (check_result != NULL) ? check_result() : (无 j 为 fail);
          if (!ok) { test_pass = false; break; }  // 直接 break，不推进 → 见 §6.2
          test_state[0..NR_CPU-1] = not_start;
          curr_test++;                             // 全代码唯一的推进点
      } else {
          while (curr_test == i) { relax; schedule; }  // 等 BSP 推进到下一格
      }
  }
```

注意 `curr_test` **不存在**「BSP 于循环开头公布 `curr_test = i`」这一步——它只在汇总通过后 `++`，起跑/收尾两道 barrier 靠的是「各核把 `test_state` 推离上一个状态」这一约定。另外两张表的空槽语义不对称：single 表**跳过**空槽继续（`test` 指针为空则略过），SMP 表**遇空槽 break**——在表中间留洞只对 SMP 侧截断。

实现小疵：无 `check_result` 的失败汇总里 `pr_error` 打印的是 `cpu_id`（执行该行的恒为 BSP），日志里的核号未必是真正失败的核。

`check_result` 判定语义：

```text
  check_result == NULL   →  每核 test() 返回值都计入，任一非 0 即 fail
  check_result != NULL   →  每核只执行 test() 标 success；
                            只 BSP 调 check_result() 判总结果，
                            每核 test() 返回值被忽略
  返回 true  → 该 case 通过
  返回 false → 该 case 失败（BSP break）
```

`test_state[cpu]` + `curr_test` 是跨核同步状态：AP 在 `while (curr_test == i)` 上自旋等待 BSP 推进，BSP barrier 内含 `schedule` 让出 CPU。

### 6.2 失败非干净收敛（必读）

- **single fail：** `break` 出循环，不打「SINGLE PASS」横幅（逐条的 PASS/ERROR 行仍已打印），但 BSP **仍会执行** smp，并在末尾 **仍可能 poweroff**。
- **smp fail：** 失败判定后 BSP `break` 且**不**执行 `curr_test++`，于是未跑完这轮的 **AP 卡在** `while (curr_test == i)`；BSP 则退出 `multi_cpu_test` 走到 poweroff。AP 的「卡」不是硬死锁——自旋里始终带着 `arch_cpu_relax()` + `schedule()`，各核照常让出，直到 BSP 关机。

不是「失败则整机一致优雅退出」。排障时不要假设「没 PASS 就一定立刻停」。

## 7. 公开 API

接口集中在两处：框架入口——`create_test_thread` / `BSP_test` / `AP_test` / `single_cpu_test` / `multi_cpu_test` 与表结构、槽上限（`modules/test/test.h`）；两张测试用例表的编排（`single_test.c` / `smp_test.c`）。各 case 的实现文件见 §8。以头文件注释为准（`test.h`；已与 `test.c` 核对）。

**本篇不涉及：** 各 case 所验证的子系统约定（MM/IPC/…见对应篇）；`RENDEZVOS_TEST` 构建开关（见 `01`）；`request_poweroff`（见 `40`）；兼容层系统调用回归。

各 `*_test` / `*_check` **不是**给兼容层的稳定 ABI——增删改表即可。

### 7.1 编排顺序（调用方须遵守）

| 角色 | 顺序 |
|------|------|
| BSP | `cmain` 调 **`create_test_thread(true)`**，执行 `BSP_test`：先 `single_cpu_test`，再 `multi_cpu_test`，常 **`rendezvos_request_poweroff`**，然后 `schedule` |
| AP | `start_secondary_cpu` 调 **`create_test_thread(false)`**，跑 `AP_test`：仅 `multi_cpu_test`，再 `schedule` |
| 加 case | 实现函数后填入 **`single_test[]` / `smp_test[]`**（≤10 槽） |

禁用：`-URENDEZVOS_TEST` 或关 json feature。

### 7.2 框架入口

```c
error_t create_test_thread(bool is_bsp_test);
void *BSP_test(void *arg);
void *AP_test(void *arg);
void single_cpu_test(void);
void multi_cpu_test(void);

#define MAX_SINGLE_TEST_CASE 10
#define MAX_SMP_TEST_CASE    10
```

| 接口 | 说明 |
|------|------|
| `create_test_thread` | `gen_thread_from_func` 挂到本核 `core_tm`。 |
| `single_cpu_test` | 顺序执行表；非 0 fail 则 `break`（**仍可能继续 smp + poweroff**）。 |
| `multi_cpu_test` | barrier + `schedule`；`check_result!=NULL` 时只信 BSP 汇总。fail 时 AP 可能卡在 `curr_test`。 |

### 7.3 表结构

`single_test_case` / `smp_test_case` 的定义与逐字段语义（含 `check_result == NULL` 时每核返回值都计入的判定）见 §4，此处不再复列结构体。无 linker section 自动注册（§1）；测试用例索引见 **§8**。

## 8. 测试用例索引（按域）

索引结构：两张静态表 + case 实现文件，编译期固定，无运行时注册。

```text
   single_test[]  (BSP 顺序)          smp_test[]  (各核并行)
   ┌─────────────────────┐            ┌─────────────────────────┐
   │ [0] {test, name}   │ ← .c 文件  │ [0] {test, name, check?}│ ← .c 文件
   │ [1]  ...            │    一一    │ [1]  ...                 │    一一
   │ ...                 │    对应    │ ...                      │    对应
   │ [9] (MAX=10)        │            │ [9] (MAX=10)            │
   └─────────────────────┘            └─────────────────────────┘
        │                                   │
        └─ 域：DSA / MM / 平台 / IPC / 时间     └─ 域：锁 / 堆 / MSQ / IPC / 调度 / 日志
```

### Single（`single_test[]`）

| 域 | 入口 / 文件 |
|----|-------------|
| DSA | `rb_tree_test` ← `single_rb_tree_test.c` |
| MM | `arch_vmm_test`；`kmalloc_test`；`page_slice_test`；可选 `pmm_test`（注释——代码注释说明它几乎占满物理帧，若启用须放表尾） |
| 平台 | `test_pci_scan`（无 `PCI` 时直接 `REND_SUCCESS`） |
| IPC/Port | `ipc_test`、`ipc_multi_round_test`；`port_discovery` ← `single_port_test.c` |
| 时间 | `single_timer_test` |

### SMP（`smp_test[]`）

| 域 | 入口 | `check_result` | CPU 数要求（`smp_test.c` 注释） |
|----|------|----------------|--------------------------------|
| 锁 | `smp_lock_test` | `smp_lock_check` | scalable |
| 堆 | `smp_kmalloc_test` | 无（每核返回值计入） | scalable |
| MSQ | `smp_ms_queue_test` / `_dyn_alloc_test` / `_check_test`（**三 case 同文件** `smp_ms_queue_test.c`，各配 `_check`） | 三个都有 | 前两个 even-only，末位 fixed-4 |
| IPC/Port | `smp_ipc_test`；`smp_port_robustness_test` | 均无 | even-only；scalable |
| 调度 | `smp_thread_affinity_test` + `_check` ← `thread_affinity_test.c` | 有 | 环状拓扑：建线程时绑定 i→(i+1)%n；check 校验 `seen[j]==prev` |
| 日志 | `smp_log_test`（`_check` 存在） | 有 | **表内常注释掉**（只看输出） |

## 9. 多架构

测试用例随 `ARCH=` 构建；PCI 等受 feature 门控——`single_pci_test.c` 整体 `#ifdef PCI`，关闭时 `test_pci_scan` 直接返回 `REND_SUCCESS`（占槽不做事）。

SMP 测试用例按 CPU 数需求分三级（`smp_test.c` 表头注释）：**scalable** 适配任意 NR_CPU≥1（锁、堆、port robustness）；**even-only** 需要成对角色，NR_CPU 为奇数时只有前偶数个核参与、其余跳过（两个 MSQ 变体、IPC）；**fixed-4** 专为 4 核设计，NR_CPU≠4 时跳过/视为通过（`smp_ms_queue_check_test`）。环状 affinity 用例随建线程时绑定 i→(i+1)%n，天然适配任意核数。
