## 评分方法（2026-11-19 起重评）

四个维度，每项满分 **100**；**总分 = 四项算术平均（四舍五入）**。

| 维度 | 含义 | 明确不计入本维 |
|------|------|----------------|
| 技术准确 | 与**当前**代码是否一致；机制、常量、调用链有无说错 | 体例、空格、引用缩写习惯 |
| 内容与说理 | 「为什么这样设计」是否讲清；重点详、次要略；有无空话 | 单句是否拗口（归阅读体验） |
| 结构条理 | 章节顺序是否先读者需要的；有无同文两述、层次乱 | 全文件名 vs 裸号（归体例债） |
| 阅读体验 | 中文是否顺、有无难读长句/歧义/指代不清；**按人读懂设计来评** | 中英半角空格、「测例」用词、引用缩号——这些记「体例债」，**不压阅读体验分** |

**体例债（不计分）：** 引用是否统一为昵称+号或裸号、中英空格、「测例/测试用例」等全书口径。写入「需改进」时可提，但**不进四维平均**。

**与旧五维的列对应（`旧评暂存` 行如何读表）：**

| 新列 | 旧列暂存写法 |
|------|----------------|
| 技术准确 | 旧「技术准确」原分 |
| 内容与说理 | 旧「内容与详略」原分 |
| 结构条理 | 旧「篇章架构」原分 |
| 阅读体验 | 旧「词句可读」原分（**含体例惩罚，偏严**；重评时会按新口径重打） |
| 总分 | 旧五维平均原分；括号内可附旧「篇章引用」分，便于对照 |
| 需改进 | **完整保留** 2026-11-15 长注；重评覆盖时再改写 |

**评分纪律：** 通读全文后才打「已重评」；`旧评暂存` 行的数字与长注来自首轮，重评前不要当最终结论，但**必须留着当核对清单**。

### 目标与底线

| 做 | 不做 |

| 按表内「余留 / 需改进」改细节：重复小节、拗句致歧义、错误锚点、可并双表、偏薄 §9 | 为涨分而改契约语义（syscall schedule、irq 属主窗、COW/VSpace 等） |

### 余留归因标签（写进「需改进」列）

每条余留必须归为下列之一（可多条并存）：

| 标签 | 含义 | 谁处理 |
|------|------|--------|
| **`[AI已改]`** | 本轮已改正文 | — |
| **`[AI可改]`** | 仍可用自动化再收（结构并节、措辞） | 下一包 AI |
| **`[需人工]`** | 设计口味、是否升格章节、是否删手册体量、代码债、待实测、Maintainer 语体 | Maintainer |
| **`[可接受]`** | 说理需要的篇幅/强调；不追求再涨分 | 停手 |

**阶段结束条件：** 全表「需改进」中不再出现未处理的 `[AI可改]`；剩余仅为 `[需人工]` / `[可接受]` / 历史 `[AI已改]` 摘要。

### 单篇流水线

1. 读该行「需改进」→ 拆成必改 / 可缓 / 需人工。  
2. 只改正文必改（对照代码锚点；**不改 core 源码**）。  
3. 四维重评覆盖该行；**打分偏低的维度必须写原因**（一句即可）。  
4. 更新下方「抬底进度」；给你 diff 摘要（每篇 ≤5 条）。

1. 结构债密集：`14`–`17`、`09`–`10`、`19`/`21`、`42`/`43`  
2. Trap 导读：`23`–`25`（`26`/`27` 手册体量默认 `[需人工]`/`[可接受]`）  
3. 其余按表扫尾；平台/测例缺口多为 `[需人工]`

Maintainer **A 档契约审定**（trap/MM/线程）仍在抬底之后单独做；见对话中的审阅建议，不在本表替代。
