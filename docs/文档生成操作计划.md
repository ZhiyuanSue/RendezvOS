# Core 文档生成操作计划（v0.1）

本文档给参与写 core 文档的人（含 AI）用。写哪一篇、写哪些章节、怎么避免重复，以这里为准。目录树在 `v0.1/full/README.md`。

代码 v0.1 已冻结；文档尚未冻结。写文档时不改 `core/` 里的代码。

---

## 文档分三块

**full/** — 与 v0.1 代码对应的全量说明：设计、数据结构、调用链、测试。每篇还要写清楚：这层能力为什么放在 core、调用方应怎么用、哪些事不该在上层再做一遍。

**compat/** — 给链接 core 的上层用的操作说明：按任务写步骤，细节链到 full，不在 compat 里复制长契约。只写 core 侧的 API 与期望，不写 Linux syscall 表，也不写上层仓库里的文档路径。

**evolution/** — 待办、已关闭项、远期设计。这里的条目不是现行契约；实现 compat 时不能只看 evolution。

---

## 怎么一篇篇写

1. 在 `v0.1/full/README.md` 里选定下一篇（按 Maintainer 定的顺序，或 README 末尾建议顺序）。
2. 读完该篇「源码」列出的头文件和 `.c`。
3. 该篇代码会调用其他模块时，整理阶段也要弄清那些接口，但**不要把别的模块写进本篇正文**：
   - 若依赖模块已有 v0.1 full 定稿 → 读该文档即可，成稿里用链接指过去（如「port 收发顺序见 `core/docs/v0.1/full/04-IPC/…` 第 n 节」）。
   - 若尚未有文档 → 直接读对应头文件与 `.c` 理解调用约定，本篇只写「调用了什么、在本流程里起什么作用」，不展开对方模块的内部设计。
4. 整理阶段如需帮助理解实现与**设计动机**，可阅读 `core/docs/old/` 里的归档稿（见「关于 old/」与「设计动机与有效性论证」）；**成稿以源码为准**，不得把旧稿整段搬进 v0.1，但**必须**把仍成立的动机用自己的话写入 §1/§2。
5. 按下面「full 单篇结构」与「full 文风约束」「设计动机与有效性论证」写正文，路径与文件名必须与 README 一致。
6. **成稿后按「每篇审查」逐项自查**（生成者侧，含设计五问）；通过后把 `v0.1/full/README.md` 里该篇**第一个**方框标为 `[x]`。
7. 交 Maintainer 审定；有修改则改稿，直至通过。通过后把该篇**第二个**方框标为 `[x]`。两个方框都为 `[x]` 才算该篇完成。
8. 若影响上层调用方式，再改 compat 里对应短文（须在该 full 篇第二个方框已为 `[x]` 之后；不要一次性写完整个 compat）。
9. 代码与已有 v0.1 文档对不上时，在 `v0.1/evolution/TODO.md` 记一条，不要在正文里猜。

compat 的正文应在相关 full 篇**第二个方框（审定）**为 `[x]` 后再写。

## 关于 old/

`core/docs/old/` 是整理期间的临时归档，以后会删除；**不属于 v0.1 文档体系**。

**允许（仅整理阶段、仅操作计划与生成者）：**

- 读 `old/` 里的旧稿，帮助理解设计意图、实现细节、历史决策。
- **专门挖掘**旧稿中的问题背景、与其它系统的对比、反例与代价分析；将仍与**当前源码**一致的论点改写进 v0.1 full（不出现 old 路径）。
- 在本操作计划里说明这一用法（即本节）。

**禁止（针对一切 `v0.1/` 下成稿，尤其 full）：**

- 出现 `old/`、`old/xxx.md` 等路径或目录名。
- 写「见旧文档」「与原 xxx.md 一致」「摘自归档」等指向旧稿的表述。
- 链接、脚注、变更记录里引用 `old/` 下任何文件。
- 把旧稿里的 AI 化排版（大表、块引用 metadata、标签式小标题）原样带入 v0.1。
- **把动机留在 old、成稿只抄 API**（等于未完成整理）。

若 old 与源码不一致，以源码为准；差异记入 `v0.1/evolution/TODO.md`，不在 full 里提 old。动机已过时的段落不要硬迁。

## 规则

1. 不改 core 代码。整理阶段也不要改 `core/docs/old/`（临时归档，以后会删）。
2. full 里只能新增 README 已列出的文件；要加篇目先改 README，经 Maintainer 确认。
3. 正文用中文。标识符、文件名、路径、API 名保持英文。
4. 同一契约只在一篇 full 里写全；别处一句带过并链接，例如：见 `core/docs/v0.1/full/03-任务与调度/15-VSpace所有权与调度切换.md` 第 7 节。
5. 交叉引用用仓库相对路径：源码如 `include/rendezvos/task/thread.h`；文档如 `core/docs/v0.1/full/...`。
6. 没跑过测试就不要写「已验证」；可写「与当前源码一致，尚未复测」。
7. 除非 Maintainer 要求，不要 git add / commit。

## 上层与 compat 的写法（full / compat 均需遵守）

core 文档描述的是 **core 的抽象边界与公开契约**，不是某一具体上层仓库或某一版兼容层实现的说明书。

**禁止**

- 在 `v0.1/full/`、`v0.1/compat/` 成稿中出现**具体上层实现**的目录名、仓库名或文档路径（例如某一兼容层目录、某一 server 集合目录、上层 monorepo 的 `doc/` 路径）。
- 写「见上层 xxx 文档」「本仓库的 yyy 层」等绑定当前工程布局的表述。
- 把「兼容层 = 某 OS 兼容实现」当作唯一目标读者（core 也可被 seL4 式、自定义微内核式等上层使用）。

**应写**

- 用**抽象称谓**：上层集成方、兼容层、链接方、单执行流 server、客户端线程等。
- 写清 core **提供什么、不提供什么**，以及上层**可以**采用的三种协作方式（直接调公开 API；经 IPC 与 core 约定线程通信；通过 hook/initcall 注入）——不预设上层目录结构。
- 必须举具体名字时，用「**例如**（仅说明可能形态，非 core 契约）」并避免路径；可写「例如拟合 Linux 或 seL4 等接口风格的上层」，但不展开 syscall 表或上层模块清单。
- 对比其他 OS 时，仅用于说明 core **故意不包含**的能力（如「不提供用户态 syscall 分发表」），不假定上层选型。

**core 树内路径**

- `core/`、`include/rendezvos/`、`kernel/`、`modules/` 等 **core 源码路径**应如实写出。
- `kernel/task/servers/` 等 **core 内示例代码**可写，须与「上层 server」区分，避免读者误以为上层目录。

compat 篇同样不得复制上层仓库的操作手册；只写「调用 core 时应怎样」，细节链到 full。

## 术语（full / compat 正文）

同一概念在全库使用同一称谓，避免「外层/上层」混指 monorepo 目录。

| 称谓 | 指什么 | 典型场景 |
|------|--------|----------|
| **链接方** | 把 core 链进完整镜像的一方 | `make -C core`、`EXTRA_OBJECTS`、引导器/DTB 镜像选择、树顶 Makefile |
| **兼容层** | 实现用户态可见语义与 server 的代码 | syscall 策略、page fault 处理、VSpace/fork 政策、port 命名与 RPC |
| **上层集成方** | 总称（总览篇可用） | 子系统篇若可区分，应写「链接方」或「兼容层」而非笼统「上层/外层」 |

**core 测例运行（统一写法）** — 在 `core/` 目录内：

```bash
make ARCH=<isa> config && make all && make run
```

core `Makefile` **无** `build` 目标；链接方树顶可自定义 `build` 并内部调用 `make -C core all`。详见 `00-总览/01-构建与链接.md` §1.1、§9。

## 已暴露的问题：机制齐、设计动机薄（2026-08-29）

初稿阶段曾出现系统性偏差：**full 能回答「有什么、怎么调」，却经常答不好「为什么这样有效」**。后果是：读文档的人（含 AI）容易把子系统看成功能清单；写材料时会把 Maintainer 随口举的几个例子当成「全部设计」。

**根因归纳**

1. **交付标准偏 API**：强调源码列表、不变量、调用链，未强制从实现里挖出全部非平凡选择并论证有效性。  
2. **读代码不够深**：只扫公开头与调用链，不读关键 `.c` 分支、注释、错误路径与跨模块耦合，就会漏掉大量设计。  
3. **old 动机未迁徙**：整理时读过，成稿只留机制摘要。  
4. **定点回灌代替逐篇重做**：用「补几段动机」冒充完成，工作不扎实。

**纠正原则**：以**当前源码**为第一真源，结合 old 中仍成立的动机与硬件笔记；成稿禁止 `old/` 路径；**按 full README 篇目顺序一篇一篇重做**；禁止用短名单概括「core 的全部设计」。

## full 是 v0.1 现行设计的最终真源

- **`v0.1/full/`**：已实现行为的**契约与设计说明**（含动机、硬件语境、布局图）。读者只凭 full 应能理解「为何这样、布局如何、和硬件怎么对上」。
- **`v0.1/evolution/`**：仅记录**尚未实现**或明确推迟的项（`TODO.md` E*、`design/` 占位）。**禁止**把现行动机、论证、审计表放进 evolution，再让 full 写「动机见 evolution」。
- **禁止**在 full 中引用：`设计深度审计.md`、`full重做进度.md`、其它文档工程草稿。进度只存在于 `core/docs/full重做进度.md`（仓库工程文件，不是契约）。
- full §10「限制与后续」可链到 evolution **E\* 编号**，但句子只能是「未实现的远期项」，不能是「设计动机见 E\*」。

## 硬件语境与启动布局链条（强制，补 2026-08-29 缺口）

old 笔记常写得很抽象；**成稿必须结合具体硬件与本仓库实现写清**，不能只留「开了 MMU / 进了长模式」一类口号。

### 哪些篇必须带硬件说明

至少：**启动/平台 boot**、**trap 与 syscall 入口**、**上下文切换（arch_switch）**、**APIC/PIC 与 GIC**、**TLB/IPI**、**PSCI**。应写清：相关寄存器/模式（如 PAE→LME→PG、TTBR0/1、EL、ICR/SIPI、GICD/GICC）、本实现用了哪些、故意没用哪些、与手册状态机如何对应（点到为止，不抄整本 SDM/ARM ARM）。

### 启动相关篇必须打通的链条

下列链条在 **`启动流程总览`** 给跨架构地图，在 **`平台启动-x86_64` / `平台启动-aarch64`** 给本 ISA 精确数字与表项；**`构建与链接`** 给链接脚本符号侧。缺任一环视为该篇未完成：

1. **链接**：`script/link/<isa>_linker.ld` 的 `kernel_virt_offset`、`kernel_start_offset`、段顺序（`.boot*` / `.init.call.*` / `.percpu` / boot 栈落点）、`ENTRY`。  
2. **产物与加载**：ELF → `objcopy` → `kernel.bin`；引导器/QEMU 把镜像放到哪一物理地址；协议（Multiboot / arm64 Image）与入口寄存器。  
3. **早期物理布局**：镜像占哪段 PA；BSS/栈/早期页表页/DTB 拷贝/UART MMIO 窗口各在哪；与「尚未交给 buddy 的保留区」关系。  
4. **早期页表**：identity / 高半如何建（几级、2 MiB 还是 4 KiB）；从低址执行跳到链接 VA 的那一次；之后是否/何时拆 identity。  
5. **进入 `cmain` 之后的布局演化**：`phy_mm_init` / `virt_mm_init` / `sys_init_map` 如何在早期表之上长出 PMM 元数据区、percpu、Map_Handler 窗口——用短因果链到内存专篇，本篇须有「时间轴上的布局快照」。

### old 笔记用法（补充）

读 `old/boot.md`、`trap.md`、`interrupt.md`、`memory.md`、`lockfree-ipc.md`、`ipc.md`、`task-thread.md` 等时：

- 把抽象句子**展开成**「寄存器/模式 + 本仓库符号 + 地址数字 / 并发不变量」写进 full。  
- **用人话写动机**：像 Maintainer 笔记那样讲清楚「本来想解决啥、和谁比、为啥不那么干」——禁止只留口号式摘要，也禁止把 old 里大段 AI 腔/英文 metadata 原样搬进 full。  
- 排障轶事可浓缩为一句设计约束（例如「故用 bin + Multiboot1」）。  
- **禁止**成稿出现 `old/` 路径；与代码冲突以代码为准；未实现差异记 `evolution/TODO.md`。  
- IPC/内存/调度等长文：优先把「同步转化、两层模型、推拉、Msg_Data 拆分、percpu 堆」等**仍成立的设计故事**写进对应 full 的 §1/§2，机制细节仍以源码为准。

## 深度读代码（强制，第一真源）

写或重做任一 full 篇之前，**必须**对该篇「源码」列表做深度阅读，不得只靠旧文或口头例子。

### 必读范围

1. **头文件**：类型、不变量注释、API 契约、`FIXME`/`NOTE`、锁/生命周期说明。  
2. **实现 `.c` / `.S`**：主路径与失败路径、错误码、与其它模块的调用、故意不做什么（early return / `#ifdef`）；**涉及 boot/trap/中断时含汇编与寄存器侧写**。  
3. **链接脚本 / 引导协议头**（启动与构建篇）：与运行地址相关的符号。  
4. **测例**（若该篇 README 或 `modules/test` 有对应）：测例在锁什么性质。  
5. **调用方（core 内）**：谁用这些 API，暴露哪些隐含契约。  
6. **old 相关长文（若有）**：动机与硬件笔记线索；与代码冲突以代码为准，**未实现差异**记 `evolution/TODO.md`（不是把动机记到 evolution）。

### 读代码时要找什么（设计发现清单）

下面是**发现清单**，不是「已穷尽的设计目录」。每篇可能挖出多条；全库远不止 IPC/映射/堆几条。

- 相对更朴素实现，代码选择了什么结构（多一层对象、per-CPU、无锁、hook、mask、窗口映射等）？  
- 注释或命名在强调什么约束（owner CPU、不得持锁调 alloc、tag 位数等）？  
- 错误路径返回什么（`-E_REND_AGAIN`、leak 而非 UAF）——往往对应刻意权衡。  
- 与相邻模块的数据流（谁分配、谁释放、谁刷 TLB、谁 schedule）？  
- **地址与模式**：链接 VA、加载 PA、早期映射、运行时窗口如何演化？  
- **硬件**：本路径依赖哪些特权级/寄存器/中断控制器能力？  
- 测例在回归什么并发或生命周期性质？

**禁止**：只根据 Maintainer 或某次对话举过的例子写动机，而声称「设计已覆盖」。对话中举的例子**永远只是子集线索**（校准理解用），**完整设计集合以代码为准、按篇挖出、随篇增补**——不得把「举例过的几条」写成 core 的设计全集，也不得因此略过未举例但代码里存在的选择。

## 设计动机与有效性论证（强制）

凡本篇源码中存在**非平凡设计选择**，成稿除「是什么」外必须写清**为何有效**。总览篇须写出从代码读出的**跨子系统因果**（条数不限，随理解加深可增补），并链到专篇——**不得**把某次讨论里的三条例子固化成「唯一故事全集」。

### 整理阶段顺序（成稿前）

1. **深度读代码**（上一节）。列出本篇发现的设计点（可工作笔记，勿提交无用草稿到 evolution）。  
2. 对照 old 补「为什么」；冲突以源码为准。  
3. 对每个重要设计点用下面「五问」自答；写进 §1/§2。答不出则标「待 Maintainer」或记 `evolution/TODO.md`，**禁止空话充数**。  
4. 按「full 单篇结构」整篇写完（或整篇重做），再自查「每篇审查」。  
5. **一篇完成后再开下一篇**（与初稿「一篇一篇生成」相同）；进度记在 `core/docs/full重做进度.md`（文档工程文件，**不是** evolution 契约）。

### 五问（每个重要设计点）

| 问 | 成稿应出现的内容 |
|----|------------------|
| **面对什么失败或代价？** | 若用更朴素方案会怎样（须与本篇代码相关，勿套用固定举例清单） |
| **和谁对比？** | 有意义的对比（服务说明本设计，不写成他系统说明书） |
| **付什么代价、换什么性质？** | 性能 / 复杂度 / 可调试性 / 可扩展性等刻意权衡 |
| **反例或思想实验？** | 一个与本实现相关的具体场景 |
| **和相邻子系统如何咬合？** | 一句因果链，链到兄弟 full 篇 |

**禁止**：§2 只有「提供 X / 不做 Y」而无实质动机（纯目录型、纯平台寄存器说明篇可放宽，须在篇首声明「本篇无非平凡策略选择，依据：…」）。

### 与「避免重复」的关系

- 某一设计的**完整论证**放在最贴近实现的一篇；其它篇短因果 + 链接。  
- 总览负责**地图与跨篇因果**，不替代专篇深度。

### 逐篇重做（本次回灌方式）

- **禁止**「只给几篇加两段动机」冒充完成。  
- **要求**：按 `v0.1/full/README.md` 目录顺序，对每一篇做：深读该篇源码 → 发现设计点 → 整篇对照新标准修订（该改 §1–§10 的都改）→ 更新 `full重做进度.md` → 下一篇。  
- 已 Maintainer 双勾的篇（如构建与链接）若重做触及契约，保留双勾并在变更记录说明「动机/结构加强，契约未改」或请 Maintainer 复审。

## full 文风约束

**结构与叙述**

- 按「full 单篇结构」写，节标题用普通中文，不用「文档角色」「authoritative」一类英文标签。
- 文首最多两三行：版本 v0.1、更新日期、本篇覆盖的源码列表；不要用整块 `>` Quote 堆 metadata。
- 以连贯段落说明为主；列表和表格只在确实需要对照时使用，不要用大表格代替正文。
- 同一契约不在多篇 full 里各写一遍完整版；需要时用一句话 + 链接到其他 v0.1 文档。

**禁止的 AI 化写法（成稿中不得出现）**

- 大量「图例」「纪律」「单一真源」「硬性规则 R1/R2」式小标题。
- 几乎每节开头的块引用 metadata（`**文档角色：**`、`**版本：**` 重复挂饰）。
- 用表格铺叙述性内容（把本该是段落的设计说明拆成两列表格）。
- 空洞套话：「本文档旨在…」「综上所述…」「值得注意的是…」堆叠。
- 过度加粗、过度编号层级（四级以下标题除非源码树真的需要）。

**语言**

- 中文叙述；代码标识符、路径、API 名保持英文。
- 句子长短正常，避免同一段里连续排比句或 checklist 口吻。

compat 正文同样遵守上述语言与「少表格、少 metadata」原则，但可更短、更步骤化。

## full 单篇结构

文件名见 `v0.1/full/README.md`。各节无内容可写「无」。

1. **概述** — 本篇范围、在 core 中的位置；**若有非平凡设计，用一两段回答「五问」中的核心动机**（细节可放 §2）。
2. **目标与边界** — 解决什么、故意不做什么；**含设计权衡与对比**（见「设计动机与有效性论证」），不得只列 API 清单。
3. **分层与调用方** — 能力为何在 core；直接调 core 还是经 server；调用方须遵守什么；与相邻子系统的因果一句。
4. **数据结构与不变量** — 主要 struct/enum、生命周期、并发约束。
5. **代码对应** — 文件、职责、关键符号（本篇是详细展开处）。
6. **流程** — 启动或调用顺序；必要时用 mermaid。
7. **公开 API** — **本篇源码拥有、供其他模块 / 兼容层调用的接口**（通常在 `include/`）。  
   - **不是**「本篇流程里调用了哪些别人的 API」——那些只在 §3/§5/§6 点名并链到对方专篇 §7。  
   - 兼容层与 core 内其他模块看到的是同一套头文件，不必拆两份清单。  
   - 本篇若只编排 / 索引、不导出符号，写 **「无（本篇不拥有公开 API；…）」**；没有就是没有。  
   - **每条接口要有说明**（参数、返回、前置条件、与相邻 API 的关系），不得只甩签名列表。  
   - **真源是 Doxygen**（`@brief` / `@param` / `@return` / `@note`）：§7 改写自现有注释。  
     - **核对实现**：写/改 Doxygen 时必须对照对应 `.c`（及真实调用方），禁止凭印象臆造参数语义、返回约定或副作用；注释与实现不一致时以 `.c` 为准并改注释。  
     - **编排顺序**：若一组 API / 单一编排入口有固定调用次序（如 `cmain`、SMP 上线、port 注册），Doxygen 与 §7 须写清该顺序（可指向 §6），不得只写「初始化」而无序。  
     - **放哪里**：有公开头、且存在 C 调用方 → 注释写在 `include/` 声明处；缺则先补头再写 §7。  
     - **例外——仅汇编跳入的入口**（如 `cmain`：由 `boot.S` 调用，无 C 调用方）：**不要**为文档单独新建 `.h`；Doxygen 写在定义所在 `.c` 上，§7 注明「真源=该 `.c`」。  
   - 体量大时按 README 篇目一篇一篇做，勿抽查冒充全文审阅。
8. **多架构** — x86_64 / aarch64 差异；riscv 仅占位则说明。
9. **测试** — 相关测例、如何跑。
10. **限制与后续** — 链到 `v0.1/evolution/`，不在这里展开未实现设计。
11. **变更记录** — 日期与摘要。

## 避免重复

一篇 full 写完整的契约，例如 VSpace 的 ref 转移、port 的 send/recv 顺序。别的篇只写「见某路径某节」。

**跨模块：** 写 IPC 时不必把线程调度再讲一遍；写线程时不必把 radix 树再讲一遍。整理时可以读依赖模块的文档或代码，成稿里只保留与本篇流程相关的调用点，其余链到该模块的 full 篇。

两篇都要写同一段时，先停，问 Maintainer 哪篇为准。

## 每篇审查

full 分两步：**生成**（撰写者 / AI）与 **审定**（Maintainer）。`v0.1/full/README.md` 里每篇有两个方框，分别对应这两步。

### 生成阶段（第一个方框）

初稿写完后、交审定之前，撰写者按下面清单自查。通过则把第一个方框改为 `[x]`；不通过则改稿，不要交审，也不要勾第一个方框。

**设计动机与有效性（对照「深度读代码」「设计动机与有效性论证」「硬件语境与启动布局链条」）**

- [ ] 已深度阅读本篇源码列表中的头文件、实现与相关测例/调用方，并据此列出设计点（非仅凭对话举例）。
- [ ] §1/§2 已对本篇重要设计点回答五问；非平凡设计篇不得只有「提供/不做」清单。
- [ ] 整理时已对照相关 old 动机/硬件笔记与当前源码；过时动机未迁入；成稿无 `old/` 引用。
- [ ] **现行动机与契约写在本篇正文**；未把动机甩到 evolution；未引用 `设计深度审计` 等工程草稿。
- [ ] 若本篇属启动/平台/构建：已覆盖「链接→加载→早期物理布局→早期页表→`cmain` 后布局演化」中本篇应负责的环节（或明确链到负责篇且该篇已写清）。
- [ ] 若本篇属 trap/中断/切换/APIC|GIC：已有足够硬件语境（模式/寄存器/控制器角色），不只列 API。
- [ ] §7：每条拥有的接口有说明；Doxygen 已与 `.c` 核对；有固定编排顺序的已写清顺序；未给「仅汇编跳入」入口凭空新建 `.h`。
- [ ] 本篇按「一篇一篇」完成整篇修订后再开下一篇；`full重做进度.md` 已更新。

**内容与范围**

- [ ] 文件路径、文件名与 `v0.1/full/README.md`（或 compat 规划）一致。
- [ ] 「源码」列表中的文件在本篇中有对应说明，无大段遗漏。

- [ ] 未把其他模块的内部设计大段搬进本篇（依赖处已链到对应 full 或仅一句说明调用关系）。

**old/ 与归档**

- [ ] 无 AI 化大表、无块引用 metadata 堆叠、无标签式空洞小标题。

**分层**

- [ ] core 边界写清楚；未写具体 OS 的 syscall 语义表、未引用具体上层仓库/目录/文档路径（见「上层与 compat 的写法」）。

以上通过后，更新 README：**第一个方框** `[x]`。

### 审定阶段（第二个方框）

Maintainer 审读初稿，可要求增删改。审定关注点：事实是否与源码一致、**设计动机是否说清「为何有效」**、分层与调用方是否清楚、文风是否符合「full 文风约束」、是否与其他 full 篇重复或侵入其他模块。

- 若有问题：撰写者改稿，Maintainer 再审；第一个方框保持 `[x]`，第二个仍为 `[ ]`。
- 若无问题：Maintainer 把**第二个方框**改为 `[x]`。

**不要**在 Maintainer 审定通过前勾第二个方框。**不要**在未勾第一个方框时就开写下一篇（除非 Maintainer 同意并行）。

compat 篇目同样在撰写与 Maintainer 审定都完成后，才在 compat 的 README（若采用双框）或 full 索引中标记完成。

全部 full 篇两个方框均为 `[x]` 后，再谈是否给文档打 tag（可与代码 tag 分开）。
